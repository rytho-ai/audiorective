title: DAW project, runtime and DAWproject
---

`@audiorective/daw` owns a small audio/MIDI project and stores it as a `.dawproject` ZIP. It has four entries and a convenience root:

| Entry                          | Owns                                                                                                                                                                                                | Environment                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `@audiorective/daw/project`    | `Project`, `MidiClip`, `sessionFor` (the Session grid), tempo map, `AudioMedia`, clip envelope (`ClipEnvelope`, `normalizeClipEnvelope`, `unityClipEnvelope`, `clipGainAt`) and `ClipStretchAnchor` | Node.js and browser, no `AudioContext` |
| `@audiorective/daw/selection`  | `selectionFor`, `ProjectSelection`: the selection shared by views and agents. Pure, outside the file and undo                                                                                       |
| `@audiorective/daw/dawproject` | The `.dawproject` codec: `openDawProject`, `openDawProjectBlob`, `saveDawProject`, `saveDawProjectTo`                                                                                               | Node.js and browser, no `AudioContext` |
| `@audiorective/daw/runtime`    | `Workspace`, `scheduleClipEnvelope`; borrows a caller-owned `AudioContext`, schedules the project through Clock and hosts WebCLAP devices. It does not import the codec                             | Browser                                |
| `@audiorective/daw`            | Re-exports all four and adds `openWorkspace`, `saveWorkspace`, `saveWorkspaceTo`                                                                                                                    | Browser                                |

A project-file tool imports only `daw/project` and `daw/dawproject`; it loads no runtime, clock or host. Headless playback of a `Project` the caller already holds imports `daw/runtime` and never loads the codec. The root entry joins the two for apps that open and save files around a running `Workspace`. Widgets render the project and recorders capture takes; `daw` and `widgets` never import each other, so the app wires them.

## Save and reopen a project

```typescript
import { Project } from "@audiorective/daw/project";
import { saveDawProject, openDawProject } from "@audiorective/daw/dawproject";

import type { MidiTake } from "@audiorective/midi";
import type { ProjectAudio } from "@audiorective/daw/project";

declare const take: MidiTake; // from @audiorective/midi/web MidiRecorder.stop()
declare const audioTake: ProjectAudio; // from @audiorective/recorder AudioRecorder.stop()
const project = new Project({ title: "Demo", bpm: 120, signature: [4, 4] });
const keys = project.addTrack("Keys", "midi");
const mic = project.addTrack("Mic", "audio");

// `take` comes from @audiorective/midi/web MidiRecorder.stop().
// `audioTake` comes from @audiorective/recorder AudioRecorder.stop().
const midiClip = project.addMidiTake(keys.id, take, 2); // placed at project beat 2
project.addAudioClip(mic.id, audioTake, 1); // placed at 1 second
midiClip.midi.edit((notes) => {
  notes[0].pitch = 65;
});

const bytes = saveDawProject(project);
const { project: reopened, warnings } = openDawProject(bytes);
const notes = reopened.tracks[0].clips[0];
if (notes.kind === "midi") {
  const events = notes.playbackEvents(); // `beat` from the clip's start, still needs your synth/Clock
}
project.dispose();
reopened.dispose();
```

A MIDI clip is always in **beats** (quarter notes): `MidiClip.time` is its position in project beats, `duration` is its length in beats, and note and event times are beats from the clip's start. Audio clips are placed in project seconds. `addMidiTake(trackId, take, time?)` takes the clip position in project beats and defaults to `take.startBeat` (0 when the recorder had no playing clock). A `MidiTake` already carries its notes, duration and non-note messages in beats from its start, so no tempo conversion happens; `RecordedAudio.startFrame/startTime` and `MidiTake.startTime` are absolute AudioContext capture positions, and Project does not infer arrangement placement from them. `MidiClip.midi` is the `MidiClip` of `@audiorective/midi` that owns the editable notes: read `clip.midi.notes.value`, change them with `clip.midi.edit(draft => ...)` or `setNotes(notes)` (selection belongs to the app, not the project). `MidiClip.duration` is the clip length in beats; it changes only through the project's clip operations (`resizeClip`, `splitClip`), which replace the clip, and notes that extend beyond it are cut at playback. `Project.tracks`, `tempoMap`, `markers` and `title` are tracked reads: an effect or `useValue` that reads one re-runs after every `Project` edit, and each read returns the current immutable snapshot. `MidiClip.time` is tracked as well.

`addAudioClip` copies the take's Float32 PCM. `saveDawProject` writes it as interleaved 32-bit float WAV in the ZIP, preserving sample values. The caller can use `Project.setVolumeAutomation(trackId, points)` for a track-volume curve; points use project seconds and `"linear"`/`"hold"` shapes: a point's `shape` is how the value goes on to the next point (`"linear"` ramps to it, `"hold"` keeps this value until it), so the last point has none and is stored as `"hold"`; a clip gain curve follows the same rule. In a `.dawproject` file the point after it carries that shape as its `interpolation` (the value arrives that way, as Bitwig Studio reads it), which the codec converts both ways. Workspace applies that curve on a separate gain stage so mute, solo and static track volume remain independent. In-memory clips reuse a cached `AudioBuffer` for the same PCM channel window. Moving a clip or changing its envelope retains that buffer. Treat in-memory `AudioClip.channels` as borrowed, read-only PCM: mutating its typed arrays in place bypasses Project revisions and the cache.

### Tempo and arrangement time

`Project.tempoMap` converts musical beats to project seconds and back. `Project.bpm` is the tempo at beat zero. `setTempoChanges` replaces the tempo map: an entry at beat 0 sets the starting tempo, and without one the starting tempo stays. The running Workspace automatically rebases Clock's absolute AudioContext tempo events. Await `workspace.flush()` when a following operation depends on the change. `Workspace.position`, `seek`, audio clips, markers and track-volume automation use **project seconds**. MIDI clips use **beats**.

Time signatures work the same way in beats: `project.signature` is the one at beat 0 and `setTimeSignatureChanges([{ beat, numerator, denominator }])` replaces the list (an entry at beat 0 sets the starting signature; the denominator is a power of two). A change starts a new bar where it sits, so a change inside a bar cuts that bar short. `project.meterMap` does the bar arithmetic that does not depend on tempo: `beatToBar(beat)` returns `{ bar, beatInBar, barStart }` (bars count from 1, `beatInBar` in quarter-note beats), `barToBeat(bar)`, `ceilToBar(beat)` and `barBeatsAt(beat)`. Changes are saved as `Arrangement/TimeSignatureAutomation` and are part of `project.edit` history. The live Workspace's clock counts bars (`"1m"` quantization) in the starting signature; the later changes are in the Project, not the clock.

```typescript
project.setTempoChanges([{ beat: 4, bpm: 60 }]); // 120 BPM until beat 4, then 60 BPM
await workspace.flush();
project.tempoMap.beatToSeconds(8); // 6 seconds
project.tempoMap.secondsToBeat(4); // beat 6
project.tempoMap.snapSeconds(4.4); // 4 seconds, the nearest beat
```

Create MIDI material with `project.addMidiClip(trackId, { duration: 4, notes }, startBeat)` or `project.addMidiTake(trackId, take, startBeat)`. MIDI follows the tempo map: tempo edits stretch its placement, note endpoints and controllers together, while audio clips stay anchored in seconds. `project.clipTimeSeconds(clip, localTime?)` maps a clip's native position plus offset (seconds for audio, beats for MIDI) to project seconds for arrangement drawing and `workspace.duration`. `setTempoChanges` replaces the full list and requires unique positive beats and positive finite BPM values. `Project.snapshot()` carries the map. DAWproject stores audio in a seconds `Clips` lane and MIDI in a beats `Clips` lane with beat content (`vel` is the note velocity 0..1), plus beat-based `Arrangement/TempoAutomation` with `hold` points. The importer also accepts a seconds-unit MIDI lane from another application and converts it to beats through the file's tempo map. It rejects unsupported tempo curves rather than dropping them.

## Long audio takes and media ownership

For a long take, stream `AudioRecorder` chunks to `AudioMediaWriter` backed by browser OPFS (`createOpfsAudioMediaWriter`, exported from `daw/runtime` because it needs browser storage; `AudioMedia` and `AudioMediaWriter` stay in `daw/project`), then add the returned `AudioMedia` to `Project`. `createOpfsAudioMediaWriter(sampleRate, channelCount)` takes the context's sample rate in Hz and a `channelCount` that must equal the recorder's channel count (the file holds interleaved 32-bit floats, so another count reads back with the wrong length and layout). The project stores a frame window and leaves the File with the caller-owned media object. Splitting, trimming and duplicating these clips retain windows into the same file rather than copying the full PCM. This sharing applies while the project and its source media remain open. DAWproject export writes each clip's retained audio window to its WAV entry. After reopening, that entry is the clip's available source: audio outside the exported window is absent, and split clips do not retain a shared full-take asset. Keep the original recording separately if later untrimming beyond those exported windows is required. Playback reads two-second chunks and waveform views can use `await media.peaks(startFrame, frameCount)` for a bounded display summary.

```typescript
import type { AudioRecorder } from "@audiorective/recorder";
import type { ProjectTrack } from "@audiorective/daw/project";

declare const recorder: AudioRecorder;
declare const track: ProjectTrack;
declare const measuredInputLatencySeconds: number;
declare function showError(error: unknown): void;
import { createOpfsAudioMediaWriter } from "@audiorective/daw/runtime";

const writer = await createOpfsAudioMediaWriter(context.sampleRate, 1);
const anchor = workspace.takeAnchor();
try {
  const recording = recorder.record({ onChunk: (chunk) => writer.writeChunk(chunk) });
  void recording.catch(showError); // failures can arrive before the Stop click
  // Later, after the user stops recording:
  const span = await recorder.stop({ result: "span" }); // same span as recording
  const media = await writer.finish(span);
  project.addAudioMediaClip(track.id, media, workspace.takePosition(anchor, span, measuredInputLatencySeconds));
  await workspace.flush();
  // Keep `media` while clips or undo history refer to it. After closing that project:
  // await media.dispose(); // deletes this temporary OPFS take
} catch (error) {
  await writer.abort();
  throw error;
}
```

The completed span's `dropouts` field is optional: a healthy take omits it, so inspect `span.dropouts?.length` or `span.dropouts ?? []`.

`AudioMedia.pending` is `true` for the media of a clip read from a compressed file in an opened `.dawproject` that no decoder has read yet (see [Save and reopen a project](#save-and-reopen-a-project)); `readFrames` and `peaks` reject for it.

`AudioMedia.peaks(startFrame, frameCount)` resolves to `{ min: Float32Array, max: Float32Array, duration: number }`. Pass that complete summary directly to the waveform; its `peaks` alternative takes a `Float32Array`, not another summary object. The frame range comes from the current clip's retained media window. File-backed audio clips expose `clip.media`, `clip.startFrame` and `clip.frameCount` directly. They are not nested under a `source` field. Re-read the current clip from `project.tracks` after a split, trim or reopen:

```typescript
import { mountWaveform } from "@audiorective/widgets/waveform";

const clip = project.tracks.flatMap((track) => track.clips).find((clip) => clip.id === clipId);
if (clip?.kind === "audio" && clip.media) {
  const data = await clip.media.peaks(clip.startFrame, clip.frameCount);
  const waveform = mountWaveform(container, { data });
  // Dispose this view when removing it; it does not own clip.media.
}
```

When the app opens a microphone for this take, release that microphone if later setup (`connect` or `recorder.ready`) fails, as well as after completion. Keep a borrowed microphone alive; its creator handles final disposal.

`AudioMediaWriter` accepts a caller-owned `AudioMediaStorage` as an alternative to OPFS. The storage must write in order and return a readable `Blob` or `File` on finish. `AudioMedia` reads interleaved little-endian float32 frames; `dispose()` releases only storage made by its writer. The application retains `AudioMedia` while any clip or undo entry borrows it. The demo removes its temporary OPFS takes when a project closes; an interrupted browser session can leave temporary files in site storage.

Use `await saveWorkspaceTo(workspace, writableStream)` or `saveDawProjectTo(project, writableStream)` to write a DAWproject ZIP without assembling the whole take or archive in a `Uint8Array`. This stream writes stored ZIP entries with CRC and size in every local header; it reads media twice and stops before classic ZIP's 4 GiB archive boundary. The demo uses a native save-file picker when the browser offers one; its download fallback and `saveWorkspace(workspace)` materialize the full ZIP in memory. Reopen from a `Blob` or `File` with `openWorkspace(context, blob, options)` for a running workspace, or `openDawProjectBlob(blob)` for a project alone, which retains WAV media as Blobs. The synchronous `saveDawProject(project)` accepts in-memory clips only and throws `Project file-backed audio needs saveDawProjectTo().` for a song that holds file-backed audio or archive entries (such as a file opened from a Blob), so no entry is ever dropped; `saveWorkspace(workspace)` streams such a song into memory itself. Each float WAV is limited by RIFF's 4 GiB length field. Both open paths verify the ZIP directory, entry sizes and CRCs before opening a project. The streaming import collects Blob parts under the browser's Blob storage policy, so actual disk versus memory use depends on the browser.

## Arrange clips and mix tracks

`Project.moveClip(clipId, trackId, time)` moves a clip on a matching track using that clip's unit (seconds for audio, beats for MIDI). MIDI moves retain the same `MidiClip.midi` for an open editor. `duplicateClip(clipId, time, trackIdOrOptions?)` takes a track ID or `{ trackId?, linked? }`, uses the source clip's unit and makes a new ID (an independent copy unless `linked`, see [Linked clips](#linked-clips)); `removeClip(clipId)` removes it. `splitClip(clipId, offset)` uses a **clip-local** position (seconds for audio, beats for MIDI). `resizeClip(clipId, { start?, end? })` moves a clip's edges to **absolute timeline positions** in the clip's unit, like `moveClip`; an omitted edge stays. Audio stays aligned in time, so moving the left edge earlier reveals earlier audio from the recording and moving it later trims. Both audio edges must stay inside the recording (`start >= clip.time - clip.sourceOffset`, `end <= clip.time - clip.sourceOffset + clip.sourceLength`), otherwise it throws and changes nothing. A MIDI clip stays aligned the same way and nothing is deleted: a start edge moves `time` and `sourceOffset` together, the end edge moves `duration`, and moving an edge back out reveals the same notes again (see [MIDI clip windows](#midi-clip-windows)); it may reach into empty content, and its `time` stays at or after 0. A moved edge has no fade; an unmoved edge keeps its fade. The clip keeps its ID and name and the edit is one `project.edit` step. `setClipSourceRange(clipId, { start, end })` instead points a clip at part of its content while `clip.time` stays: the duration becomes `end - start`. An audio clip takes recording seconds, the same fade rule applies (a fade survives only at an edge whose recording position did not move) and the range must lie inside the recording (`0 <= start < end <= clip.sourceLength`); a MIDI clip takes content beats, any finite `start < end`, and keeps its notes. On a looped clip the range is the new loop and the point the clip starts from, and the clip keeps its `time`, `duration` and fades; on a time-stretched clip it is in seconds of the stored (stretched) audio and keeps the ratio, so it can only narrow the clip (see [Edit a clip in detail](#edit-a-clip-in-detail)). A time-stretched clip may shrink, but extending it throws: set its ratio to 1 first. The left split clip keeps the original ID. Audio boundaries round to samples. `splitClip` on a MIDI clip makes two independent clips that each keep all the notes (the left keeps the original ID); `resizeClip` and `setClipSourceRange` keep the clip's `midi` object, so an open editor stays valid but must re-read the clip's `time`, `duration` and `sourceOffset`. These operations replace the clip object and do not rewrite stored note positions when tempo changes. Rename with `setTitle(title)` and `setTrackName(trackId, name)`, or remove a whole track with `removeTrack(trackId)`. Structural edits update `Project.cells.revision` (note edits through `MidiClip.midi` are in `Project.cells.content`); read `Project.tracks` again after an edit. `Project.setMarkers([{ time, name }, ...])` stores sorted, unique section markers in project seconds; `Project.markers` exposes the current snapshot. DAWproject stores these under standard arrangement `Markers`.

Tracks have `muted`, `solo` and `pan` (`-1` left, `0` center, `1` right), alongside linear `volume`. Use `Project.setTrackMuted`, `setTrackSolo` and `setTrackPan`; a running `Workspace` applies each in the task turn that made the edit (no `flush()` needed for the sound to change), and a burst of fader moves is applied in order without a click. Solo follows the graph to and from a bus, and mute wins over solo. Each track and bus is an `@audiorective/effects` `Channel` strip; the runtime writes `Project` values into its params and the project stays the only owner.

### Edit a clip in detail

To let a user choose which part of a recording a clip plays, show the clip's **whole recording** in the toolkit's selector with the current window selected, audition the selection, then apply. `project.clipRecording(clipId)` returns the whole recording in the shape clips use: in-memory `channels` or file-backed `media` (`startFrame` 0 and all `frameCount` frames), plus `sampleRate` and `duration` seconds. It works for timeline and Session slot clips, shares the clip's data (no copy) and is a tracked read. A MIDI clip or an unknown ID throws. A time-stretched clip's recording is the stretched audio it stores.

`workspace.auditionAudioClip(clipId, { range: { start, end } })` plays that part of the recording (recording seconds, the unit of `sourceOffset` and of the selector's selection) through the same audition path, replacing any running audition. The range plays raw: the clip's fades, gain automation, stretch and loop do not apply, and it may reach outside the clip's window. It must satisfy `0 <= start < end <= recording.duration`.

```typescript
import { WavePlayer } from "@audiorective/player";
import { mountWaveformSelector } from "@audiorective/widgets";
import type { AudioClip } from "@audiorective/daw";

// Double-click on a clip: open the editor on a dedicated player that only draws the recording.
async function openClipEditor(clip: AudioClip, root: HTMLElement) {
  const recording = project.clipRecording(clip.id);
  const channels = recording.media ? await recording.media.readFrames(0, recording.frameCount) : recording.channels;
  const buffer = new AudioBuffer({ length: channels[0].length, sampleRate: recording.sampleRate, numberOfChannels: channels.length });
  channels.forEach((channel, index) => buffer.copyToChannel(channel as Float32Array<ArrayBuffer>, index));
  const player = new WavePlayer(context);
  await player.load(buffer);
  // Recording seconds equal player seconds: the player loads the buffer unstretched.
  player.setSelection({ start: clip.sourceOffset, end: clip.sourceOffset + clip.duration });
  const selector = mountWaveformSelector(root, { player, controls: false });
  const close = () => {
    workspace.stopClipAudition();
    selector.dispose();
    player.dispose();
  };
  return {
    audition() {
      const range = player.cells.selection.value;
      if (range) void workspace.auditionAudioClip(clip.id, { range }); // the part of the recording, through master volume
    },
    apply() {
      const selection = player.cells.selection.value;
      if (selection) project.edit("Set clip range", () => void project.setClipSourceRange(clip.id, selection));
      close();
    },
    cancel: close,
  };
}
```

The player and selector are the editor's own; disposing them leaves the clip, the project and its media untouched. `setClipSourceRange` keeps `clip.time`, so the clip stays where it sits on the timeline and plays the chosen part of the recording from there.

### Linked clips

`project.duplicateClip(clipId, time, { trackId?, linked: true })` makes a MIDI clip that **shares the source's notes**. The copy has its own ID, position, length, window (`sourceOffset`), name and loop, but `clip.midi.edit` or `setNotes` on any clip of the group changes all of them, as one Undo step inside `project.edit`; playback and offline renders hear the edit on every placement without `needsSync`. The group shares the whole timeline content, notes and the clip's non-note MIDI events (as a DAWproject `reference` does), so `addMidiClip(trackId, data, time, { linkedTo })` ignores the `notes` and `events` in `data` and uses the source's; only `duration` and `sourceOffset` are its own. Undo or redo that would rewrite notes shared with a clip outside the step returns `conflict` and changes nothing when that clip was edited since. Only MIDI clips link (an audio clip cannot share content), and a copy made by `copyRange` or `duplicateScene` is always independent. A group can span the timeline and Session slots: `sessionFor(project).copyToArrangement(slot, { atBeat, linked: true })` places a slot clip on the timeline sharing its notes, and `copyToSlot(clipId, slot, { linked: true })` puts a linked copy of a timeline or slot clip in a slot (see [Session scenes and clip slots](#session-scenes-and-clip-slots)). A pattern stored in a scene and placed linked on the timeline is edited once; `renderSession`, live Session playback and the timeline all hear the edit. `addMidiClip(..., { linkedTo })` takes a slot clip's ID too.

- `project.linkedClips(clipId)` returns the other clips sharing this clip's notes (timeline clips first in track and time order, then Session slot clips in scene and track order), empty when it is not linked; the ID may be a timeline or slot clip. It is a tracked read. `overview()` shows the same as `linkedTo: string[]` on a clip in `tracks` and in `session`, and `findClips()` on timeline clips; it is omitted when the clip is not linked.
- `project.makeClipUnique(clipId)` (a timeline or slot clip) gives that clip its own copy of the notes it has now; the rest of its group stays linked. It does nothing for a clip that is not linked. The `applyEdits` operation is `{ type: "makeClipUnique", clip }`.
- `resizeClip` (either edge), `setClipSourceRange`, `setClipLoop`, `moveClip` and `removeClip` keep the clips linked: each member has its own `time`, `duration`, `sourceOffset` and loop over the shared content, so no edit of a window needs `makeClipUnique`. `splitClip` makes independent copies of the notes for both pieces; `rippleDelete` does the same wherever it splits a clip, and a `copyRange` copy is always independent. `editNotes` edits reach every placement.
- `.dawproject` saves write the group's notes once, in the first clip's `<Notes id>`, and every other clip as `<Clip reference="…"/>` with no content of its own (each keeps its own `playStart`, `playStop` and loop); opening resolves each `reference` back to one shared note list, so a reopened project keeps its groups. Files from other programs that use `reference` on beats-time MIDI clips open the same way.

### Edit a project as one undoable step

`project.overview()` returns a JSON-safe summary with the current `version`: the tracks with their timeline clips, and `session`, the scenes in order, each with the clips of its filled slots (`id`, `name?`, `kind`, `trackId`, `trackName`, `duration` and its `unit`, seconds for audio and beats for MIDI; a MIDI clip also lists `sourceOffset` and its `loop`). `project.findMarker({ name, occurrence })` and `project.findClips({ trackId, trackName, range, relation })` locate content; ranges are half-open beats. Pass the version you read to `applyEdits`:

```typescript
const { version } = project.overview();
const receipt = project.applyEdits({
  expectedVersion: version,
  label: "Repeat chorus, late vocal",
  ops: [
    { type: "copyRange", range: { startBeat: 32, endBeat: 48 }, atBeat: 48, placement: "insert", as: "chorus" },
    { type: "moveClip", clip: { fromCopy: "chorus", trackName: "Vocals" }, position: { byBeats: 1 } },
  ],
});
if (receipt.status === "applied") project.undo({ expectedVersion: receipt.version });
```

The request is plain JSON. Operations run in order and publish together. `status: "conflict"` means the Project changed since `expectedVersion`; `status: "rejected"` carries a `code` and the failing `opIndex`. Neither changes the Project. `copyRange` with `placement: "insert"` opens room at `atBeat` on every track: later clips, tempo changes, markers and volume automation move later and keep their musical position, and a clip crossing `atBeat` is split. `applyEdits` rejects a request whose final arrangement puts a clip it moved, resized or created (`moveClip`, `duplicateClip`, `addMidiClip`, `copyToArrangement`, the pieces of `copyRange`) on top of another clip, so adjacent clips can move together in any order; `rippleDelete` overlaps the pieces it joins for its crossfade on purpose. A position may give `atBeat`, `atSeconds` or both when they name the same moment at the tempo map as it is at that step (within 1e-6 s); both that disagree are rejected, so put tempo changes first in `ops`. The `applied` receipt also lists `changedTracks`, `removedTracks`, `changedScenes` (scenes that stay and were renamed or moved in the order, with the scenes beside the move; filling or clearing a slot is a clip in `created`, `changed` or `removed`), `removedScenes` and `song` (any of `"tempo"`, `"timeSignature"`, `"markers"`, `"title"`, `"masterVolume"`), each empty when nothing of that kind changed; a whole-list operation (`setTempoChanges`, `setTimeSignatureChanges`, `setMarkers`, `setVolumeAutomation`, `setTrackEffects`, `setTrackRouting`) that gets the list the Project already has changes nothing. A receipt's `copies[as]` maps each source clip to its copy. An operation with a field its type does not take (`{ type: "moveClip", clip, position, by: 2 }`) is rejected with `invalid-operation` naming the allowed fields, instead of being ignored.

**Notes.** Three operations change the notes of a MIDI clip (timeline or Session slot), in content beats (the beats of `clip.midi.notes`; see [MIDI clip windows](#midi-clip-windows)). They join the request's one undo step, and a stale `expectedVersion` is a `conflict` like any other:

- `{ type: "addNotes", clip, notes: [{ pitch, start, duration, velocity? }] }`: `pitch` is an integer 0 to 127, `start` is 0 or more, `duration` is more than 0, `velocity` is 0 to 1 (default 0.8). IDs are generated and reported in the receipt: `receipt.createdNotes` has one `{ clipId, ids }` per `addNotes` operation, with `ids` in the order of that operation's `notes` (empty when the request adds none).
- `{ type: "removeNotes", clip, noteIds }`: an ID the clip lacks rejects with `note-not-found`.
- `{ type: "editNotes", clip, notes: [{ id, pitch?, start?, duration?, velocity? }] }`: an omitted field stays; an entry that changes nothing is rejected.

Linked clips share notes, so an edit reaches every placement. A note outside the clip's window is still editable; it just does not play.

**Every edit has an operation.** Each public editing method of `Project` and `ProjectSession` has a JSON operation of the same name (`type` is the method name; fields are its parameters, with positions named `atBeat` or `atSeconds`): clips (`splitClip`, `duplicateClip`, `removeClip`, `moveClip`, `setClipLoop`, `addMidiClip`, `setClipName`, `setAudioClipEnvelope`, `setAudioClipGainAutomation`), tracks and mixer (`addTrack`, `removeTrack`, `setTrackName`, `setTrackVolume`, `setTrackMuted`, `setTrackSolo`, `setTrackPan`, `setTrackRouting`, `setTrackEffects`, `setTrackRackPreset`, `setTrackMacroValue`, `setMasterVolume`, `setVolumeAutomation`, `setControllerLane`), the song (`setTitle`, `setTempoChanges`, `setTimeSignatureChanges`, `setMarkers`), devices (`removeDevice`, `moveDevice`) and the Session grid (`addScene`, `renameScene`, `moveScene`, `removeScene`, `duplicateScene`, `setMidiClip`, `moveSlotClip`, `clearSlot`, `copyToSlot`, `copyToArrangement`). The methods that need PCM, plug-in bytes or are not edits have none; [MCP](./mcp.md#coverage-method-to-operation) lists each with its reason and every operation's fields.

**Naming what a request makes.** An operation that makes clips, tracks or scenes takes `as: "name"`. A later step selects the clips as `{ fromCopy: "name" }` in `clip`, and a track or scene as `{ fromCopy: "name" }` in `trackId` or `sceneId`, so one request can add a track, put a MIDI clip on it and add notes. The receipt has `createdTracks` and `createdScenes` (`[{ id, as? }]` in operation order) next to `created`, `createdNotes` and `copies`.

**Overlaps.** Clips on one track may overlap: `addAudioClip`, `addMidiClip`, `moveClip`, `duplicateClip`, `resizeClip` and `splitClip` never reject one, and playback and renders sound every clip (layered placements and `rippleDelete`'s `crossfade` rely on it). Only an `applyEdits` request rejects a clip it moved, resized or created that ends on another clip in the final arrangement (`code: "overlap"`), because an agent's JSON request is checked before it is published; audio positions that round to the same frame are not an overlap. A page that wants the same guard on direct calls checks the neighbours' `time` and `duration` (or `project.findClips({ trackId, range })`) before calling.

`{ type: "rippleDelete", range, crossfade? }` removes a time range from the whole song, where `range` is a `TimeRange`: `{ startBeat, endBeat }` or `{ startSeconds, endSeconds }`, half-open. Call it directly as `project.rippleDelete(range, { crossfade })`; unlike single-step Project methods it is always one step: on its own it records one Undo step labelled "Ripple delete" and a failure part-way changes nothing; inside an open `project.edit` it joins that step, and that edit rolls it back if the error leaves the callback. Every clip after the range moves earlier by its length, in the clip's own unit (audio by seconds, MIDI by beats; a range in one unit converts to the other through the tempo map as it was before the edit). A clip across the start keeps the part before it, a clip across the end keeps the part after it, a clip across both becomes two clips, and a clip inside it is removed, all through `splitClip`, `resizeClip` and `removeClip`, so ids, names, untouched fades and the whole recording behind each audio clip stay. Markers inside the range are removed and later ones move earlier. Tempo changes inside it are dropped, later ones move earlier by the beats, and the tempo in effect at the range's end applies from its start, so the music after the cut keeps its tempo and lands at exactly `oldSeconds - length`. Track volume automation drops the points inside the range, moves later ones earlier and adds a point at the range's start with the curve's value at its old end. Clip gain automation is source-relative and stays. `crossfade` (`true` for a short 5 ms crossfade, `false` or omitted for a hard cut, or a length in seconds) overlaps the audio pieces that meet at the range's start, centred on the join: the left piece's end extends by half and the right piece's start moves earlier by half into the real recording, and `fadeOut` and `fadeIn` are set to the overlap. A side with less hidden audio shrinks the overlap to twice what the smaller side can give. MIDI is not crossfaded. Inside `project.edit` the cut joins that Undo step; called alone it changes content without one, and through `applyEdits` it is one labelled step. An invalid range or crossfade throws and changes nothing (`applyEdits` rejects with `invalid-operation`).

`project.edit(label, () => { ... })` groups synchronous calls to the clip, note, tempo, marker, volume-automation and Session grid methods into one edit, and rolls them all back if the callback throws. It is the entry for gestures that need PCM or other non-JSON data. Project methods called outside `edit` or `applyEdits` apply immediately but are not recorded in undo. The mixer value setters (`setTrackVolume`, `setTrackPan`, `setTrackMuted`, `setTrackSolo`, `setTrackMacroValue`, `setDeviceParameter` and `setMasterVolume`) are the one case with a second rule: called directly, outside an edit, they make no Undo step and no new `project.cells.version` (a running Workspace still applies them and `cells.revision` still advances); inside `edit` or `applyEdits` they are part of that edit and the version advances. So an edit that sets the same value overwrites a direct move without a conflict. Everything the song holds joins the step: clips, notes, tempo, meter, markers, scenes, devices, volume automation, adding and removing tracks (with their clips, devices, volume automation and the routes that pointed at a removed bus), and the mixer (title, master volume, track name, volume, mute, solo, pan, routing, inserts and macros). Undo of a step returns `conflict` when a later change touched what the step edited (a clip, device or route on a track it would take away, an ID it would give back, or a mixer value it set).

`project.undo()` and `project.redo()` step through one history shared by every caller, up to 50 edits; `project.cells.history` holds the next labels. Undo returns `conflict` and leaves the Project alone when a later change touched what that edit changed. An unrelated change, such as a fader move, does not block it, and a mixer edit is judged per value: an edit that set a track's level conflicts with a later change to that level only, not with a later mute, macro or insert change on the same track, which Undo leaves in place (the same for the title and the master level). Passing `expectedVersion` makes any later change to the song a conflict. `project.cells.version` covers structure and note edits and every mixer change made inside an edit; a mixer value written directly (a fader, pan, mute, solo, macro, device parameter or master level moved outside `edit` and `applyEdits`) does not advance it, so a continuous fader sweep does not make another writer's `expectedVersion` stale. Capturing live plug-in state during a save does not advance it either.

### Loop a region

`workspace.loop` repeats a beat range on the audio clock:

```typescript
workspace.loop.setRegion({ startBeat: 16, endBeat: 32 }); // bars 5-8 in 4/4, half-open
workspace.loop.setEnabled(true);
workspace.loop.cells.enabled.subscribe((on) => button.setAttribute("aria-pressed", String(on)));
```

The wrap is sample-accurate and does not depend on the main thread. Audio clips and file-backed media are cut at the region's edges, tempo changes inside it repeat, volume automation restarts with it, and a MIDI note still held at the end gets its note-off, with changed controllers restored. A note that began before the region's start is not retriggered at a wrap. A controller with no value before the region keeps its last value across the wrap, except sustain and pitch bend, which reset. `setRegion` and `setEnabled` apply while playing without restarting what is sounding. Playback before the region runs into it, and a seek past its end plays on. `workspace.position` stays inside the region while it repeats. `takePosition` places a take by the loop that was playing when its anchor was captured. `workspace.transport` keeps counting continuous beats, so read `position` for the arrangement location.

The loop is playback state: it is not saved, not in undo, and not in exports or `renderMixRange`.

### Share what is selected

`selectionFor(project)` from `@audiorective/daw/selection` returns the one `ProjectSelection` of that Project, so separate views and agent tools share it by passing the Project. `selection.state` is a tracked cell of `{ trackId, clipIds, openClipId, noteIds, range }`, plain JSON. Change it with `selectClips`, `toggleClip`, `selectTrack`, `selectRange`, `openClip`, `selectNotes` and `clear`. It is outside the file, undo and `project.cells.version`. Deleted content leaves the selection by itself and stays out even if an undo restores it. Zoom, scroll and tools stay in the app, and the playhead stays on `Workspace`.

### Check an edit before handing it back

Clips can have a non-unique name, saved as the standard DAWproject clip name. Read it with `project.clipName(clipId)`, set it with `project.setClipName(clipId, name)` or a `setClipName` operation, and filter with `findClips({ name })` or a `fromCopy` selector. Renaming never touches playback.

`renderMixRange(workspace, { expectedVersion, range, trackIds, prerollSeconds, seamBeats })` renders a range of the full mix (`{ startBeat, endBeat }` or `{ startSeconds, endSeconds }`; seconds convert to beats through the live tempo map) offline, through every device and effect, without interrupting playback. It returns stereo PCM with `peakDbFS` and BS.1770 `loudnessLUFS`, or `status: "conflict"` when the version moved. `prerollSeconds` warms delays and reverbs and is discarded. The default is 2 seconds, or back to the first MIDI clip when that is earlier, because held notes and controllers need their history. A shorter explicit value returns `historyTruncated: true`. Each entry of `seams` compares the step at a beat with the 50 ms around it; `hasClick` also fires for a hard attack placed exactly on that beat.

`trackIds` renders only those tracks, to hear or measure one part alone. Each selected track sounds through its own devices, instruments, inserts, volume, pan and automation, the bus it outputs to and the master, so the PCM equals a live solo of the same tracks (within 1e-6 of the live capture). It follows the solo rule of the mixer: send returns (effect buses a selected track feeds) are included, selecting a bus also brings in the tracks that feed it, a muted track stays silent (mute wins over solo), and the project's own solo flags are ignored for that render. `peakDbFS`, `loudnessLUFS` and `seams` measure the sum of the tracks that sound. The live Project, its version and playback are untouched. An empty list or an id that is not a track throws a `RangeError`.

### Render a session, export WAV

`renderSession(workspace, { scenes, expectedVersion?, tailSeconds?, signal? })` renders Session scenes offline, back to back, through the same mix as `renderMixRange` (track volume, pan, mute and solo, sends, effects, devices, instruments, master). `scenes` is a list of scene IDs in play order and may repeat (`[b, b, b, b]`, `[a, a, b, c]`). The Arrangement is not heard, the song is not changed and live playback is not interrupted; the render runs on a copy, so no second Project or Workspace is needed. It returns `{ status: "rendered", version, audio, durationSeconds, starts, peakDbFS, loudnessLUFS }`, where `audio` is stereo PCM from the first scene's start, `starts` holds the second where each entry of `scenes` begins, and `status: "conflict"` comes back when `expectedVersion` is given and the version moved. `tailSeconds` (default 2) lets reverbs and delays ring out after the last scene.

Scenes follow the rule of the live `playChain`, so an export equals what the chain plays: each scene starts where the previous one ends and lasts as long as its longest slot clip (a bar when no slot has a clip), which puts scenes on bar lines when the clips are whole bars. A clip shorter than its scene repeats until the scene ends, as a launched clip loops; an empty slot is silent for that scene. Track volume automation applies as under a live chain with `workspace.arrangement.value = false`: it follows the song time counted from 0, while the Arrangement's clips are not heard.

`encodeWav` (from `@audiorective/daw`, re-exported from `@audiorective/core`) turns any rendered PCM into a file; see [Encode WAV](./core.md#encode-wav).

```ts
import { sessionFor } from "@audiorective/daw/project";
import { encodeWav } from "@audiorective/daw";
import { renderSession } from "@audiorective/daw/runtime";

const [verse, chorus] = sessionFor(project).scenes;
const result = await renderSession(workspace, { scenes: [verse.id, verse.id, chorus.id] });
if (result.status === "rendered") {
  const url = URL.createObjectURL(encodeWav(result.audio, { bitDepth: 24 }));
  const link = Object.assign(document.createElement("a"), { href: url, download: "song.wav" });
  link.click();
  URL.revokeObjectURL(url);
}
```

`renderMixRange` returns the same `audio`, so `encodeWav(result.audio)` bounces an arrangement range the same way.

`await workspace.editStatus(version)` waits for queued edits and returns `"applied"`, `"needs-sync"`, `"failed"` or `"superseded"`. `saveWorkspace(workspace, { expectedVersion })` and `saveWorkspaceTo(workspace, destination, { expectedVersion })` refuse to write a Project that has moved on.

### Apply Project edits to the live graph

Workspace batches edits made directly to its Project and applies changes to clips, tempo, mixer settings, volume automation, routes, built-in inserts and hosted patch state. It can also add or remove a bus with no new hosted device while preserving other tracks and transport.

- Use `await workspace.flush()` when the caller must wait for application, such as before inspecting a new bus node or triggering a newly added clip. Observe `workspace.cells.error` for application errors. `flush()` rejects with the failed edit's cause.
- Observe `workspace.cells.needsSync.value` when adding or removing ordinary tracks. Call `await workspace.sync()` to rebuild the graph and stop transport at the current position. Existing audio nodes and hosts remain loaded until the rebuild. Changes to the hosted device list of tracks that stay do not need it (see [Editing a running project](#editing-a-running-project)).
- `workspace.checkpoint()` waits for light edits, folds live plug-in state into `Project` and returns it. `saveWorkspace()` and `saveWorkspaceTo()` call it before encoding.

`Project` keeps its content in one private store that only its methods write; a multi-field edit such as `setTempoChanges` commits once. `Project.title`, `tracks`, `tempoMap`, `markers`, `masterVolume` and `clipTimeSeconds()` are tracked reads of that store, and `project.cells.revision` counts its commits. A MIDI clip's notes belong to its `MidiClip.midi`, so a note edit does not advance `revision`; `project.cells.content` re-runs for structural commits and for note edits, and `content.value.midi.get(clipId)` holds that clip's current `notes` and `duration`. Read it from an effect that must notice every saved change, such as a dirty flag. Workspace playback and `.dawproject` saves read the note models directly, so they always see the current notes. Commands (`duplicateClip`, `resizeClip`, `splitClip`, `snapshot`, `MidiClip.playbackEvents`) and the `Workspace` commands read content untracked, so calling one inside an `effect` does not subscribe it. `MidiClip.time` is trackable on the clip. `workspace.cells.warnings` and `workspace.cells.warnings.value` expose the same read-only warning snapshot.

`Project.masterVolume` is a linear gain, initialized to `1`. Set it with `project.setMasterVolume(volume)`; a running Workspace applies it in the same task turn. DAWproject stores the value in its main channel. The companion audio export applies it to `mix.wav`. Track stems are tapped before master gain.

### Clip volume and fades

Call `Project.setAudioClipEnvelope(clipId, { gain, fadeIn, fadeOut })`; the running Workspace applies the edit. Use linear gain and clip-local seconds. Gain and fade edits share the original PCM. Trimming and splitting preserve fades on retained edges and start new edges with zero fade. PCM trims share their original backing allocation. File-backed clips continue to read only scheduled windows.

Playback applies the same envelope to in-memory clips and file-backed windows, including after a seek into a fade. Session PCM loops apply the envelope on each pass. Fades are written to DAWproject clip attributes in seconds. Audiorective keeps the constant gain in its project metadata, alongside the unmodified audio.

### Clip envelope helpers

`ClipEnvelope`, `normalizeClipEnvelope`, `unityClipEnvelope` and `clipGainAt` come from `@audiorective/daw/project`; `scheduleClipEnvelope` comes from `@audiorective/daw/runtime`. `ClipEnvelope` holds a linear `gain` and the edge fade lengths `fadeIn` and `fadeOut` in seconds. Validate values with `normalizeClipEnvelope(settings, duration)`. The unity default is `{ gain: 1, fadeIn: 0, fadeOut: 0 }`.

`clipGainAt(envelope, duration, seconds)` evaluates a clip-local position. `scheduleClipEnvelope(gainParam, envelope, duration, { when, offset, length })` installs the linear ramps on a borrowed gain parameter over a playback window. Supply absolute audio-clock seconds for `when` and clip-local seconds for `offset` and `length`. A window starting partway through a fade starts at that fade's existing level. The caller owns PCM, playback scheduling, and the temporary gain node.

### Clip gain automation

`project.setAudioClipGainAutomation(clipId, points)` edits a clip's own linear gain curve. Point times are seconds in the original source before stretch. The curve multiplies the clip's constant gain and fades, and track automation runs separately. A gain-only edit updates playing Arrangement voices at their current source position. Use `await workspace.flush()` when a following operation needs the applied change.

Moving, stretching or warping a clip preserves its points. Trimming or splitting updates `clip.gainAutomation.sourceStart` to the first retained source frame in seconds. Points outside the visible window still guide interpolation. Use `audioClipTimeMap(clip)` to convert waveform seconds with `sourceStart + map.outputToSource(playbackTime)` and use `map.sourceToOutput(sourceTime - sourceStart)` for the inverse. Pass the clip's warp output times as the overlay's `viewBreakpoints` so the drawing follows the same slopes as playback. Pass an empty array to clear the curve.

PCM, file-backed playback, clip and range audition, and newly launched Session PCM apply the curve. An already launched Session clip uses the curve from its launch. Audiorective stores editable points in its DAWproject metadata. Use the rendered audio fallback for other DAWs that need the audible result.

### Audition an arranged audio clip

Call `await workspace.auditionAudioClip(clipId)` to play the current clip window from its start, including trims, stretch and its gain envelope. It works with in-memory and file-backed clips. The audition goes through master volume, bypasses track devices and mixer settings, and leaves the Arrangement playhead and transport alone. The clip may be on the timeline or in a Session slot. Observe `workspace.cells.auditioningClip` (also `workspace.auditioningClip`) for the active or loading clip ID. A new request replaces the old one. Use `stopClipAudition()` to cancel, or let the clip finish. Committing an edit that replaces the clip stops its audition. `auditionAudioClip(clipId, { range: { start, end } })` instead plays that part of the clip's whole recording (`project.clipRecording`), in recording seconds and raw: fades, gain automation, stretch and loop do not apply, and the range may lie outside the clip's window; it replaces and stops like a whole-clip audition. See [Edit a clip in detail](#edit-a-clip-in-detail).

For a standalone player over one source, use [WavePlayer](./player.md#waveplayer) and its source-local selection. Workspace resolves a project clip's current media window and streams file-backed audio in bounded reads.

### Audition a range across audio tracks

Call `await workspace.auditionRange({ start, end }, { trackIds })` to repeat one project-second selection through master output. Omit `trackIds` to include all audio tracks. The same clock schedules the entire preview. Short tracks stay silent until the next common repeat, and the selected audio uses existing PCM and file chunk caches.

Observe `workspace.cells.auditioningRange` for the active or loading range, and call `stopRangeAudition()` to stop it. A new clip or range audition replaces the previous preview. Changes to the selected tracks' clips stop the preview. Auditions include clip gain and fades, bypass the track mixer and preserve the Arrangement position. MIDI and track device playback remain in Arrangement.

### Clip windows over a recording

Every audio clip is a window over a longer recording. `clip.sourceOffset` is the seconds into the recording where the clip's audio begins and `clip.sourceLength` is the recording's total seconds, so `resizeClip` may reveal audio up to `clip.time - sourceOffset` and `clip.time - sourceOffset + sourceLength`. Splitting, resizing and moving keep the recording, and a PCM clip's samples after an extension equal the original take. A file-backed clip's recording is its `AudioMedia`, and its offset comes from `startFrame`. `duplicateClip` and `addAudioClip` start a new recording from the clip's current window. For a time-stretched clip `clip.stretch.source` carries the same two fields: the stretch source is a window of the original recording, so a save names the original file.

Saving writes each recording once, whole, as `audio/<clipId>.wav` named after the first clip that uses it, and gives each clip `playStart` and `playStop` (seconds in that file) when it shows only part of it. Pieces cut from one take therefore share one file. `openDawProject` decodes each file once and gives every clip using it the same recording, so a reopened piece can be extended into audio that a neighbour or a deleted clip hid. A time-stretched clip is saved as its original recording with warp markers, not as a render (see [Pitch-preserving clip stretch](#pitch-preserving-clip-stretch)). Files without `playStart` and `playStop` open as one whole-file clip.

### MIDI clip windows

A MIDI clip is a window over its content, like an audio clip over its recording. `clip.midi` holds all the notes and events in **content beats**, and `clip.sourceOffset` is the content beat where the clip's start sits: the clip plays content `[sourceOffset, sourceOffset + duration)`, or its loop (see [Loop a clip](#loop-a-clip)). A new clip has `sourceOffset` 0, so its content beat equals its clip-local beat. `sourceOffset` may be negative, which shows empty content before the first note (extending a clip's start edge past its first note does this).

- `resizeClip` moves the start edge by changing `time` and `sourceOffset` together, so the content stays where it is on the timeline, and the end edge by changing `duration`. No note is deleted or edited: trimming hides notes, moving the edge back reveals them unchanged.
- `splitClip(clipId, offset)` makes two independent clips that both keep the full content: the left keeps `sourceOffset` and gets `duration = offset`, the right starts `offset` later with `sourceOffset += offset`. A looped clip keeps its loop on both pieces and the right piece continues where the loop was.
- `setClipSourceRange(clipId, { start, end })` slides the window over the content in content beats and keeps `clip.time`: `sourceOffset = start`, `duration = end - start`. On a looped clip the range is the loop and the start instead (a slip): `loop = { startBeat: start, endBeat: end }`, `sourceOffset = start`, and `time` and `duration` stay, so the clip keeps filling the same stretch of the timeline and repeats the new part; `start` must be `>= 0` there, as for `setClipLoop`.
- Playback, offline renders and the Session play the window only. A note crossing a window edge is shortened at playback and the stored note is untouched; a note-off is sent at the window's end, the latest controller values before the window are applied at its start, and a sustain pedal still down at the window's end (or the clip's end) is released there, even when no later event follows.
- A `copyRange` copy and a `rippleDelete` piece are windows too, so they keep the content their source had behind the window.
- Note edits through `clip.midi` edit the content, wherever the window is. Show the window in the piano roll with `pianoRollModel(clip.midi, { duration, window: { start: clip.sourceOffset, end: clip.sourceOffset + clip.duration } })`: notes outside it are drawn dimmed and the rest is shaded (see [MIDI](./midi.md)).
- `project.overview()` and `findClips()` list `sourceOffset` (and `loop`) on every MIDI clip; `applyEdits` has `{ type: "resizeClip", clip, start?, end? }` (absolute project beats) and `{ type: "setClipSourceRange", clip, start, end }` (content beats for MIDI, recording seconds for audio, seconds of the stretched audio for a time-stretched clip). Both are one undo step and, on a timeline clip, reject a request that ends with the clip on top of another (`code: "overlap"`).
- A `.dawproject` file stores a window that does not start at content beat 0 as `playStart` (the clip's `sourceOffset`) and `playStop` (`sourceOffset + duration`) on the `Clip`, in beats; a clip with `sourceOffset` 0 writes neither. Opening reads `playStart` (default 0, may be negative) and takes the length from `duration`; `playStop` only has to lie after `playStart`, so a file from another program that writes `playStart` on a `Notes` clip opens as a window over those notes.

### Loop a clip

`project.setClipLoop(clipId, loop)` makes a clip repeat part of its content for as long as the clip lasts, in the Arrangement, in the Session and in offline renders; `setClipLoop(clipId, null)` removes it. `clip.loop` is `undefined` without one. A MIDI clip takes a `BeatRange`, `{ startBeat, endBeat }`, in content beats (the unit of its notes and of `sourceOffset`; with `sourceOffset` 0 clip-local beats equal content beats); any positive end is allowed. An audio clip takes a `SecondsRange`, `{ startSeconds, endSeconds }`, in seconds of its recording, the frame `sourceOffset` uses, and `endSeconds` may not pass `sourceLength`. `0 <= start < end` holds for both. It replaces the clip, so inside `project.edit` Undo and Redo restore it, and `duplicateClip` keeps it. A time-stretched clip cannot loop, and stretching a looped clip drops its loop. `setClipLoop(id, null)` on an audio clip plays the recording straight on from `sourceOffset`, so it cuts the clip to the audio the recording holds from there (`end <= sourceLength`) and drops a fade-out whose edge moved.

`setClipSourceRange(clipId, { start, end })` on a looped clip slips it: the range becomes the loop and the point the clip starts from (`sourceOffset = start`), and the clip keeps its `time` and `duration`, so it fills the same stretch of the timeline and repeats the new part. A MIDI `start` must be `>= 0`; an audio range must lie inside the recording. Fades and gain automation stay with the clip (the automation's `sourceStart` moves with the new start).

A looped clip plays its content from its start (`sourceOffset`) up to the loop end, then repeats `[start, end)` until the clip ends. A clip whose `sourceOffset` is at or past the loop end enters the loop at its start. `resizeClip` may then extend the right edge without limit; audio may pass the end of the recording. The left edge keeps its rules: a clip trimmed on the left starts where its playback was (its `sourceOffset` moves to the content beat or recording second being played), and extending it to the left moves `sourceOffset` earlier. The loop itself is in content units, so no edge move changes it. `splitClip` on a looped clip keeps the loop on both pieces.

Audio repeats play as one `AudioBufferSourceNode` with `loop`, `loopStart` and `loopEnd`, so the seams are sample-accurate for PCM and file-backed clips alike (a file-backed clip reads the frames from its entry point to the loop end once and loops that buffer). MIDI repeats the notes that start inside the loop on every pass and cuts each note at the loop end; the clip's own notes are the only copy, so a note changed through `clip.midi` changes in every repetition, and notes after the loop end never play. A note that began before the loop's start is not retriggered on the repeats. Offline renders (`renderMixRange`, `exportAudioFallbackTo`) use the same scheduler.

The Session launches a looped audio clip as a launcher buffer clip over the whole recording with `loop: { startBeat, endBeat }` set to the loop's seconds (`bpm: 60`, so one beat is one second of the recording) and `offsetBeats` at the entry point: the clip starts at its `sourceOffset` and then repeats the loop. Fades are not applied in the Session; the clip's gain and gain automation are, read at recording seconds. A clip shorter than its first pass loops only up to where the Arrangement stops (the same holds for a MIDI loop that ends after the clip). File-backed audio has no Session clip. A MIDI clip in the Session plays one stretch of its content on every pass: its window `[sourceOffset, sourceOffset + duration)`, or for a looped clip the loop alone, `[startBeat, startBeat + min(loop length, duration))`, so a pass never replays the notes before the loop. The lead-in before a loop and an entry inside it are Arrangement-only; `renderSession` renders the same stretch.

Gain automation repeats with the loop: its point times are seconds of the recording, and on every pass the curve is read at the position being played (the first pass from `sourceOffset` to the loop end, later passes from the loop start to its end). Edge fades set at the recording's start and end therefore smooth every seam, and the value steps from the curve at the loop's last frame to the curve at its first. A left trim moves `sourceStart` by the recording distance. Known limit: a file-backed clip whose first pass starts far before its loop decodes everything from the entry point to the loop end into memory as one buffer (a loop that contains the entry reads only the loop); a clip that enters at or inside the loop is the efficient case.

A `.dawproject` file stores the loop as `loopStart` and `loopEnd` on the `Clip`, in its `contentTimeUnit`: seconds of the recording for audio, beats for MIDI (a MIDI clip in a seconds lane reads back as beats). Audio clips also write `playStart`, the clip's `sourceOffset`, and `playStop` = `playStart` + the clip's duration, capped at the end of the recording: where the audio would stop if it did not loop. Audiorective reads the window from `playStart` to the end of the recording and the clip's length from `duration`; `playStop` is advisory and must only lie after `playStart` and inside the recording, so a file whose `playStop` marks the content or loop end opens. It requires `loopStart < loopEnd` with the loop inside the recording. Files without loop attributes open as before.

### Pitch-preserving clip stretch

`Workspace.prepareAudioClipStretch(clipId, ratio, processor, { anchors?, signal? })` borrows a `WaveStretchProcessor`. Pass the desired length divided by original length. Call `apply()` on the prepared result inside the app's undo transaction, then await `workspace.flush()` if the next action depends on the applied render. Preparation leaves Project unchanged. Moving, trimming, deleting or replacing the clip invalidates a prepared edit. Preparing a newer result for that clip, cancelling the supplied signal and disposing Workspace all cancel outstanding work. Apply a prepared result once.

The example borrows the app's existing `history` manager: its synchronous `record(label, apply)` captures Project state before and after `apply`. Finish asynchronous preparation before entering that transaction; record only the synchronous application, then flush outside it. `history` belongs to the app, rather than a Workspace export.

```ts
import { TimeStretch } from "@audiorective/effects/time-stretch";

declare const history: { record(label: string, apply: () => void): void }; // the app's undo manager
const processor = await TimeStretch.load({ wasmUrl: "/wasm/rubberband.wasm" });
try {
  const edit = await workspace.prepareAudioClipStretch(clipId, 1.5, processor);
  history.record("Stretch audio clip", () => edit.apply());
  await workspace.flush();
} finally {
  processor.dispose();
}
```

A clip stores its rendered playback plus the original audio window. A later ratio always uses that original window. Pass ratio `1` without anchors to restore it without a processor. Clip position and ID stay in place. Fade lengths scale with the clip. Offline processing loads the selected source window into memory.

To warp a clip, pass strictly increasing interior `{ sourceFrame, outputFrame }` anchors and an anchor-capable processor. For 48 kHz PCM, `{ ratio: 1, anchors: [{ sourceFrame: 48000, outputFrame: 62400 }] }` moves the point from 1.0 to 1.3 seconds while holding total length. Trimming or splitting projects each cut back to a retained source frame and rebases interior anchors. `audioClipTimeMap(clip)` exposes `sourceDuration`, `outputDuration`, `sourceToOutput(seconds)` and `outputToSource(seconds)`. Its piecewise-linear conversion also projects source-relative gain into playback time.

A stretched clip is saved in the form Bitwig Studio writes: the outer clip's place and fades, and inside it one nested clip whose `Warps` play the **original** audio file (`Audio algorithm="stretch"`, written once, named after the first clip that uses it) through the clip's time map. The `Warp` points are the clip's ends and each anchor, plus a point wherever the song's tempo changes inside the clip, because a warp that is steady in beats is not steady in seconds across a tempo change. Another DAW stretches the clip with its own engine. The clip's pitch-correct render is stored beside this in the folder `audiorective/render/` (one float32 WAV for all clips cut from or copied from the same render) with a `render` record in `audiorective/state.json` that names the original file, the window, the clip's length, a hash of the window's samples, the ratio and the anchors. Another DAW ignores the folder, and Bitwig drops it when it saves. A reader opens the clip with that render, with no stretch processor and no warning, as long as the record still equals the file's `Warps`; if the warp points, the tempo or the audio file changed, or the folder is gone, it ignores the render and opens as described under "Stretched audio from another DAW". A clip that is only a varispeed placeholder (no processor was available) stores no render, and a clip rendered on open stores its render. A stretched clip therefore adds its rendered audio to the size of the file (the original window plus a render of the stretched length). A save of an opened clip that did not change leaves its XML untouched; an edit (move, trim, resize, split, duplicate, fades, gain, name) rewrites only the values that changed, keeps the nested form and the original file path, and regenerates the `Warps` from the time map only when the clip's window or speed changed. A file this package wrote before this form (the rendered WAV as the clip, the original in `audiorective/source/` and the ratio in the details entry) still opens with the render as playback and is saved in the new form. Use `project.hasFileBackedAudio` to choose a streaming save when a clip's recording is file-backed.

#### Stretched audio from another DAW

A `.dawproject` that another DAW wrote can hold audio of one tempo in a song of another (Bitwig Studio writes `Warps` with `Audio algorithm="stretch"` and `Warp` points). The reader turns such a clip into an audio clip with `stretch = { ratio, source, anchors? }`: `source` is the window of the original file the markers cover, `ratio` is timeline seconds over audio seconds through the tempo map (`round(frames * ratio)` is the clip's length in frames, so it is within 1/frames of the exact quotient), and each interior place where the speed changes becomes an anchor (a warp marker that changes the slope, or a tempo change inside the clip). Markers whose speed equals the tempo map's (a clip dropped in at its own tempo) stay ordinary clips. The clip's playable audio is a **varispeed placeholder** made with core `resamplePCM`: exactly `round(frames * ratio)` frames at the source's rate, every segment between anchors resampled to its own length, so the clip has the right length and each anchor lands on its frame while the pitch moves with the speed.

Pass a stretch engine to get the pitch back. `WorkspaceOptions.stretch` takes the same `WaveStretchProcessor` as `WavePlayerOptions.stretch`; `TimeStretch` from `@audiorective/effects/time-stretch` fits (see [Effects](./effects.md)). `openWorkspace`, `Workspace.create` over an opened project and `workspace.open` render every stretched clip with it, pitch preserved, before the song plays, through the path `prepareAudioClipStretch` uses. This is not an Undo step and does not change `project.cells.version`: the clip is the same clip with better audio.

```ts
import { openWorkspace } from "@audiorective/daw";
import { TimeStretch } from "@audiorective/effects/time-stretch";

declare const workletUrl: string; // your bundler's URL for the AudioWorklet module
const stretch = await TimeStretch.load({ wasmUrl: "/wasm/rubberband.wasm" });
const workspace = await openWorkspace(context, bytes, { workletUrl, stretch });
```

| Situation                             | What plays                                                                           | `workspace.cells.warnings`                                                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `stretch` given                       | The engine's render, pitch preserved                                                 | Nothing                                                                                                                               |
| No `stretch`                          | The varispeed placeholder: right length and position, pitch moved by the ratio       | One message per opened song, naming how many clips and that passing a `stretch` processor (for example `TimeStretch`) fixes the pitch |
| The engine fails on one clip          | That clip's varispeed placeholder; the song still opens                              | `Audio clip "<name>" could not be stretched with the stretch processor (<error>); it plays with a changed pitch.`                     |
| The file's algorithm is not `stretch` | The varispeed audio is the final audio: the file asks for it, so nothing is rendered | Nothing                                                                                                                               |

Offline renders (`renderMixRange`, `renderSession`, `exportAudioFallbackTo`, `renderStems`) read the rendered audio from the Project the live workspace plays, so they never play a different pitch than the live song; `workspace.deviceOptions` carries `stretch` for a render workspace of your own. `openDawProject` alone (no Workspace) has no engine: the clip carries its ratio and its varispeed audio. A clip whose source the reader keeps file-backed or compressed (a WAV of a Blob archive, Ogg, MP3, FLAC) is decoded to PCM by `openWorkspace` / `openDawProjectBlob` first; read directly with `openDawProject`, a compressed one stays in the file unplayed with a warning.

**Tempo edits.** A clip stores seconds, a Bitwig `Warp` is in beats. When the song's tempo changes in the app, a stretched clip keeps its seconds and its ratio (it does not follow the beats, like every audio clip); on save the `Warp` times are written in beats from the current tempo map, with a point at each tempo change inside the clip, so the saved file reopens as the same clip in this reader. Bitwig, which derives the speed from the beats, plays it at the same speed over the clip's span.

## Mixer buses and sends

Use `Project.addTrack(name, "bus")` for a submix or pass `{ busRole: "effect" }` for a shared effects return. Both have the same rack, fader and automation as other tracks. Route a track's main output to one bus or to the master, then add separate post-fader, post-pan sends with linear gains. The model rejects unknown targets and feedback cycles before changing the graph.

```ts
const drums = project.addTrack("Drums", "midi");
const keys = project.addTrack("Keys", "midi");
const wet = project.addTrack("Echo return", "bus", { busRole: "effect" });
project.setTrackEffects(wet.id, [{ id: "echo", type: "delay", delayTime: 0.3, feedback: 0.35, enabled: true, wet: 1 }]);
await workspace.flush();

for (const [id, gain] of [
  [drums.id, 0.3],
  [keys.id, 0.15],
] as const) {
  project.setTrackRouting(id, { outputBusId: null, sends: [{ busId: wet.id, gain }] });
}
```

`Project.setTrackRouting()` works with or without a live Workspace; a running Workspace rewires in the task turn that made the edit, without replacing devices or stopping the transport (a track added or removed in the same change waits for `sync()`). Flush for a deterministic routing readback. Removing a destination restores incoming main outputs to master and drops sends to the removed bus. Soloing a return keeps its inputs and suppresses their parallel dry outputs. `workspace.trackMixerOutput(trackId)` borrows a post-fader node for a meter. Exported individual stems are taken there, before downstream bus processing, while the exported mix passes through all buses.

Routing saves to DAWproject channel destinations and post-fader sends. DAWproject files with pre-fader sends, extra send controls or other unsupported routing are rejected. The [DAWproject schema](https://github.com/bitwig/dawproject/blob/main/Project.xsd) defines those wire formats.

## Live browser workspace

```typescript
import { Project } from "@audiorective/daw/project";
import { Workspace } from "@audiorective/daw/runtime";
import { openWorkspace, saveWorkspace } from "@audiorective/daw";

const project = new Project({ bpm: 120 });
const track = project.addTrack("Synth", "midi");
const workspace = await Workspace.create(context, project, {
  destination: context.destination,
  workletUrl: "/assets/webclap-worklet.js",
});
// Reads the CLAP ID, name, vendor and version from the bundle and adds the device as one Undo step; playback keeps running.
const device = await workspace.addWebClapDevice(track.id, "/plugin/oxo-synth2.wclap");
const iframe = document.querySelector<HTMLIFrameElement>("#plugin-editor")!;
const host = workspace.host(device.id); // lookup by device ID, not track ID
const detachEditor = host?.hasEditor ? await host.mountEditor(iframe) : undefined;
await workspace.play();
workspace.seek(1.5);
project.setTrackVolume(track.id, 0.7);
project.setVolumeAutomation(track.id, [
  { time: 0, value: 1, shape: "linear" },
  { time: 2, value: 0.5, shape: "hold" },
]);
await workspace.flush();
const bytes = await saveWorkspace(workspace); // checkpoints live plug-in state, then encodes
detachEditor?.();
workspace.dispose();
project.dispose(); // `create` borrows the project, so the caller disposes it

const reopened = await openWorkspace(context, bytes, {
  destination: context.destination,
  workletUrl: "/assets/webclap-worklet.js",
  resolveBundle: ({ pluginId }) => (pluginId === device.pluginId ? device.bundleUrl : undefined),
});
// Inspect reopened.cells.warnings.value and reopened.project before playing.
```

A file written by another application may hold audio the reader does not decode itself (Ogg Vorbis, Opus, MP3, FLAC, AAC, AIFF: whatever the browser decodes). `openWorkspace` and `workspace.open` give each such file to the context's `decodeAudioData`, resample the result to the context's rate with core's `resamplePCM` as `importAudioFiles` does, and open the clips as ordinary in-memory clips, so a file plays the same imported or opened, and the offline renders (`renderMixRange`, `renderSession`, `renderStems`, `exportAudioFallbackTo`) hear it. This happens before the song starts, and a large file costs its decode time at open. A file the browser cannot decode is named in `workspace.cells.warnings`, and its clips stay in the file unchanged, silent. Saving writes every compressed file back with its original bytes and path, edited clips included. The decoded start is the browser's: an MP3 with the LAME/Xing gapless header starts exactly, and one without it plays its encoder delay (1105 samples) late, because nothing in the file says otherwise. With `openDawProject` alone (Node, no decoder) the clips still exist with their place, length and window, and their `clip.media.pending` is `true`: they can be moved, trimmed and saved, but not read or played. `Workspace.create` over such a Project cannot play them, so open the file with `openWorkspace` instead.

`workspace.addWebClapDevice(trackId, bundleUrl, { pluginId? })` is the way to put a plug-in on a track from a bundle URL alone: it loads the bundle once to read its identity, so no descriptor field is copied by hand and none can be guessed wrong, then adds the device with `project.addDevice` inside `project.edit("Add <name>")`, so `project.undo()` takes it away again, and waits until the running track has it. It returns the `WebClapDevice`. `pluginId` picks one plug-in of a bundle that holds several. A bundle that fails to load rejects with the host's error and leaves the Project unchanged; if the plug-in then fails to start, the step is undone. Playback does not stop: the new plug-in is loaded off to the side and spliced into that track's chain, and the other tracks play on. The edited track may glitch for a moment while its chain is rewired, and a MIDI track now plays through the plug-in (the track's `instruments` entry is used again when its last device goes). A pending track-list change (`cells.needsSync`) is applied first, by a `sync()`, which stops playback. Undo and Redo of a device step, `project.moveDevice(deviceId, index)` and `project.removeDevice(deviceId)` inside `project.edit` all apply the same way, and the plug-in's last state goes into the step, so Redo brings it back as it was. Use `project.addWebClapDevice` directly only when the Project is built without a browser (a server, a test) and the identity is known.

### File > Open in a running app

`openWorkspace` makes a **new** Workspace, so everything the page bound to the old one (mixer strips, `cells.error` and `cells.levels` subscriptions, the Loop button over `workspace.loop`, widgets over `workspace.project`) would have to be torn down and rebuilt. Use it for the first load, or when a second, separate engine should open the file (a render workspace on another context). For File > Open in an app that is already running, keep the Workspace and replace its song:

```typescript
import { Project } from "@audiorective/daw/project";
await workspace.open(bytes); // Uint8Array, Blob, File or a Project; options: { resolveBundle?, instruments?, stretch?, workletUrl?, warnings?, ownsProject? }
await workspace.open(new Project({ bpm: 120 })); // File > New: an empty or in-memory song
```

`open` reads the file (a `Project` you pass is used as it is) and fully loads the new song (plug-ins, restored device state, instruments) off to the side before it touches the running one. A bad file, or a plug-in load that throws, rejects with the same error `openWorkspace` throws and the current song keeps playing unchanged. On success, in one step: playback stops at 0; `workspace.project` becomes the opened Project (the Workspace owns a Project it read from a file and disposes the Project it replaces if it owned that one; a project you passed to `Workspace.create` or `open` stays yours unless you give `ownsProject: true`, the same option `Workspace.create` takes, and then the Workspace takes it over once `open` succeeds and disposes it when it is replaced; a call that rejects never disposes a `Project` you passed); `cells.warnings` hold the new file's notices; `cells.needsSync` and `cells.error` clear; `cells.session` yields a new launcher and `cells.levels` follows the new tracks. The Workspace, `cells`, `loop`, `player` and `output` are the same objects, so effects and subscriptions that read `workspace.project` or `workspace.cells.*` keep firing without rebinding. Edits you make to the passed `Project` while it loads are applied right after the swap: light edits (clips, mixer, tempo) play at once, a track added or removed sets `cells.needsSync`. Anything you derived from the old Project (track ids, clip ids, a mixer UI keyed by track id, an undo history) belongs to the old song and must be rebuilt from `workspace.project` inside an effect.

The loop is playback state, not file content, and its region is in the old song's beats, so `open` clears it: `loop.cells.region` becomes `null` and `loop.cells.enabled` becomes `false`, and a Loop button bound to those cells follows. Options you pass replace the workspace's own for this song and later `sync()`s; options you leave out stay. Opening while playing stops playback; call `play()` again for the new song.

`Workspace` owns runtime nodes and Clock. The caller owns its context and any `Project` passed to `Workspace.create`, and disposes that project separately. A disposed Project rejects edits and saves. A Workspace from `openWorkspace` owns the project it opened: `workspace.dispose()` disposes it (disposing it again is harmless). Pass `{ ownsProject: true }` to `Workspace.create` to hand a project over the same way; `workspace.open` ends that ownership by disposing the song it replaces. `workspace.host(device.id)` returns the loaded plug-in host, if available. `workspace.cells` holds every observable value as a read-only cell: `needsSync`, `error`, `warnings`, `session`, `auditioningClip` and `auditioningRange`. `workspace.position` and `workspace.duration` are project seconds for external playheads and seek controls. For a MIDI piano roll, pass `project.tempoMap.secondsToBeat(workspace.position) - clip.time` as its playhead (beats from the clip's start). `sync()` rebuilds routing after changing tracks or devices (`cells.needsSync` reports when), preserving the playhead and stopping playback. MIDI note edits refresh Clock while playing. `pause`, `stop` and `seek` fade out active arrangement sources and release hosted instruments. Playback schedules a live start ahead on the audio clock. Play and seek wait for file-backed chunks at the target and request later chunks ahead of the playback window. A seek made while playing keeps `clock.state` and `player.isPlaying` at `playing` during that wait: the playhead holds at the target, nothing sounds, and audio resumes from the exact requested frame (a `play()` during the wait resolves when it has). A media read that fails is reported once in `cells.error` and its clip is skipped for the rest of that playback run; the next `play()` or `seek()` reads it again, and a successful read clears the error (a replaced or removed clip never inherits it). A missing or mismatched bundle yields a warning and leaves that track's device silent. `workspace.cells.warnings` (also `workspace.cells.warnings`) is a frozen array of these notices plus file-open notices passed through `WorkspaceOptions.warnings` (`openWorkspace` supplies them first); it is a tracked read, never mutated in place, and each new notice replaces it.

For recorded takes, capture `const anchor = workspace.takeAnchor()` before arming `AudioRecorder`; use `workspace.takePosition(anchor, take, measuredInputLatencySeconds)` when adding the result to `Project`. For `MidiRecorder`, capture the anchor the same way before `record()`; `takePosition` returns project seconds, so convert it with `project.tempoMap.secondsToBeat(...)` before `addMidiTake`, whose position is project beats. A recorder attached to the playing Workspace clock already carries `take.startBeat`, which `addMidiTake` uses by default. `takePosition` maps the actual take start to project seconds while transport plays; while transport is stopped, it keeps the anchor's project cursor. `takeAnchor(audioTime)` maps that audio time to project time, so an anchor taken in the short lead `play()` leaves before the audible start is exact too: a take that starts before the transport's start is placed earlier by the same offset (and throws below project zero, as with latency). An anchor captured while a seek waits for media cannot be placed, because the audible start is not known yet; capture it after the seek resumes. A positive measured input latency moves the placement earlier. If that would cross project zero, the method throws instead of silently losing timing; record with preroll or reduce the correction. The demo exposes a locally stored millisecond correction field in its browser panel and defaults to zero until the user measures their device.

### Track and master levels

`workspace.cells.levels` is a tracked `ReadonlyCell<{ master: number; tracks: Record<string, number> }>` of post-fader peaks in dBFS, `-Infinity` when silent, the convention of the effects `Channel` `cells.level` it reads for each track. `master` is measured after the master volume, and `tracks` holds one entry per live track ID, so a track added or removed (`sync()`) appears or leaves. The values refresh every animation frame while the context runs and fall to `-Infinity` when playback stops or the context is suspended. Sampling starts on the first read and ends on `dispose()`; an offline render workspace never reads it, so it never builds the analysers.

```ts
import { effect } from "alien-signals";
import type { ProjectTrack } from "@audiorective/daw/project";

declare const track: ProjectTrack;
declare const meter: { set(track: number, master: number): void }; // your meter view
effect(() => {
  const { master, tracks } = workspace.cells.levels.value;
  meter.set(tracks[track.id] ?? -Infinity, master);
});
```

The cell holds the instantaneous peak. Peak hold and fall-back ballistics belong to the view: `mountLevelMeter` takes this dBFS value as its `source` and draws it as given, with no hold of its own, so hold the maximum in your callback if the UI needs a hold marker.

### Extensions

An extension is app code that adds to a song what the DAWproject format has no place for: its own data, and named operations an app or an AI assistant can call. Music content (tracks, clips, notes, mix, devices, tempo, markers, scenes) stays in the Project itself; an extension is for the rest. It is not an audio plug-in.

```ts
import { defineExtension, defineOperation } from "@audiorective/daw";

const songChain = defineExtension({ id: "groovebox.chain", defaultValue: (): number[] => [] });
const chain = project.extension(songChain); // chain.value, chain.subscribe(...)
project.edit("Add scene B", () =>
  chain.update((scenes) => {
    scenes.push(1);
  }),
); // one Undo step, a new song version

const removeGap = defineOperation({
  name: "podcast.remove-gap",
  description: "Remove a time range from every track and close the gap.",
  input: { type: "object", properties: { start: { type: "number", minimum: 0 }, end: { type: "number", minimum: 0 } }, required: ["start", "end"] },
  run(project, { start, end }: { start: number; end: number }) {
    if (!(end > start)) throw new RangeError("Remove gap needs end after start.");
    // split, remove and move clips with Project methods
    return { removedSeconds: end - start };
  },
});
project.operations.register(removeGap);
project.operations.list(); // [{ name, description, input, readOnly }] for a menu or an AI tool list
project.operations.call("podcast.remove-gap", { start: 10, end: 20 }); // one Undo step

// Show agents what the data means, and offer a question that is not an edit:
const patterns = defineExtension({
  id: "patternbox.patterns",
  defaultValue: (): { name: string; bars: number[]; clipIds: string[] }[] => [],
  summary: (list) => list.map(({ name, bars, clipIds }) => ({ name, bars, clipIds })), // plain JSON for read_project
});
const listPatterns = defineOperation({
  name: "patterns.list",
  description: "List patterns with the bars where each is placed.",
  input: { type: "object", properties: {} },
  readOnly: true, // a query: no Undo step, cannot change the song
  run: (project) => project.extension(patterns).value,
});
project.extension(patterns).value; // open it once so project.extensionSummaries() includes it
project.extensionSummaries(); // [{ id: "patternbox.patterns", summary: [...] }]
```

- **Data.** `defineExtension({ id, version?, defaultValue, validate?, summary? })` describes JSON data; `project.extension(definition)` returns the song's data for it. `value` is tracked, `subscribe` reports every change including undo, redo and opening a file. `set` and `update` change it like any Project method: inside `project.edit` they join that Undo step, on their own they change the song version without an Undo step. `update` changes a mutable copy in place or takes the value the recipe returns (`count.update((n) => n + 1)`); data left equal is no change. Values are frozen JSON (no functions, dates, `undefined`, holes or non-finite numbers). Data saved by a newer `version` of the extension reads as `defaultValue()` and `set` refuses to overwrite it, so an older app cannot damage it.
- **Summary.** `summary(data)` is an optional, agent-facing view of the data: plain JSON (same rules as the data) that says what it means, such as `[{ name: "A", bars: [1, 3, 5], clipIds: [...] }]`, in the app's own words and ids the agent can use with the Project's clip operations. `project.extensionSummaries()` returns `[{ id, summary }]` for each extension that defines one and that this song has opened with `project.extension(definition)` (open each at startup); the MCP `read_project` shows the same list as `extensions`. An extension without `summary` is never shown, so raw data does not reach an agent unless the app chooses to. Keep it small: it is read on every `read_project`. It is not part of `overview()`, which describes the music only. A summary that is not JSON throws.
- **Files.** The data is saved as `extensions/<id>/data.json` inside the `.dawproject` archive with its `version`; other DAWs ignore it. Opening a file restores it; `validate(data, version)` checks or migrates it, and data it rejects reads as `defaultValue()` while staying in the file until the app changes it. An app that does not define an extension keeps its data unchanged when it opens, edits and saves the file. Any other archive file this codec does not use is kept and written back unchanged too; a file that this save writes itself takes precedence.
- **Operations.** `defineOperation({ name, description, input, run, label?, readOnly? })` takes its arguments as a JSON Schema object (the shape AI tool calls use). `project.operations.call(name, args)` checks types, required names, number ranges and field names (an object with `properties` rejects any other field unless its schema sets `additionalProperties: true`), then runs `run(project, args)` as one Undo step labelled `label` (default `description`); if `run` throws, nothing changes. Called inside `project.edit`, it joins that step, and `run` may itself use `project.edit` and `project.applyEdits`: inside an open edit both join its Undo step (`applyEdits` still rehearses first and changes nothing when it rejects, and its receipt then lists no clips). Operations belong to one Project object: register them again on a Project opened from a file. **Queries.** `readOnly: true` makes the operation a question: `call` returns the result of `run` with no Undo step and no version change, `list()` reports `readOnly`, and any Project method that changes the song inside `run` (including `set` on an extension and `project.edit`) throws and changes nothing; a note edit made directly on `clip.midi` (`edit` or `setNotes`) throws before it changes anything, so use a normal operation for writes. (A `MidiClip` from the midi package takes a write guard with `setWriteGuard`; the Project installs one on its clips while a query runs.) `run` must be synchronous, and its result should be JSON when an agent calls it.

### Page-made instruments

A MIDI track without a WebCLAP device can play a sound the page makes itself. `WorkspaceOptions.instruments` maps track IDs to core [`Sampler`](./core.md) options (`sound`, `rootNote`, `release`, `polyphony`, `volume`); the Workspace builds one `Sampler` per track and plays that track's notes into its mixer channel, so volume, pan, mute, solo, sends and inserts apply. It plays in Arrangement, Session, `renderMixRange` and the audio fallback export, which rebuild the sampler on their own context through `workspace.deviceOptions`.

```ts
import type { SoundFactory } from "@audiorective/core";
import type { ProjectTrack } from "@audiorective/daw/project";
import { Workspace } from "@audiorective/daw/runtime";

declare const kickTrack: ProjectTrack, keysTrack: ProjectTrack;
declare const pianoBuffer: AudioBuffer;
const kick: SoundFactory = (context, hit) => {
  const osc = new OscillatorNode(context);
  osc.frequency.setValueAtTime(150, hit.when);
  osc.frequency.exponentialRampToValueAtTime(50, hit.when + 0.1);
  const gain = new GainNode(context);
  gain.gain.setValueAtTime(1, hit.when);
  gain.gain.exponentialRampToValueAtTime(0.001, hit.when + 0.3);
  osc.connect(gain);
  return { output: gain, sources: [osc], duration: 0.3 };
};
const workspace = await Workspace.create(context, project, {
  instruments: { [kickTrack.id]: { sound: kick }, [keysTrack.id]: { sound: pianoBuffer, rootNote: 60, release: 0.2 } },
});
```

`instruments` can also be a function `(track) => TrackInstrument | undefined` that receives each MIDI track's `id`, `name` and `kind`. It runs for every MIDI track without a device, including tracks added before a `sync()`, so a saved song reopens without mapping names to ids first:

```ts
import { openWorkspace } from "@audiorective/daw";
import type { SoundFactory } from "@audiorective/core";

declare const kick: SoundFactory;
declare const pianoBuffer: AudioBuffer;
const sounds: Record<string, { sound: SoundFactory | AudioBuffer; rootNote?: number }> = {
  Drums: { sound: kick },
  Keys: { sound: pianoBuffer, rootNote: 60 },
};
const workspace = await openWorkspace(context, bytes, { instruments: (track) => sounds[track.name] });
```

A note starts a voice at its time with its velocity (0..1 scales the level; the sampler plays the level of the MIDI byte, `round(velocity * 127) / 127`, whether the note came from the Arrangement, a Session clip or `renderSession`, so a live Session and its render match) and is released at its end over `release`, so a one-shot sound longer than its note is cut there unless `release` is long enough. A `SoundFactory` returns the voice unstarted; the sampler starts and stops it. The instruments are code, not file content: pass the same option to `openWorkspace` or `Workspace.create` after opening (track IDs survive save and open). A track with a device plays the device and ignores its entry.

The sampler plays what a sampler can: notes, and the **sustain pedal** (CC64, down from value 64, one pedal for every channel). A note-off that falls while the pedal is down releases at the next pedal-up (it keeps sounding until a pedal-up is scheduled); all-notes-off (CC120, CC123) releases at once. Everything else is ignored, so a track lane or a clip event for it has no sound on a sampler: pitch bend, mod wheel and every other controller, channel and polyphonic pressure, and program change. Use a WebCLAP device when those must be heard.

### Resolve saved plug-in bundles

Bundle URLs from project files are hints. An app approves a URL by returning it from `WorkspaceOptions.resolveBundle`, or returns `undefined` to decline. This applies to both workspace open functions and to `Workspace.create` with a project read by the codec.

To open a file saved from a running workspace with the same plug-ins, pass `workspace.deviceOptions`: it asks that workspace's `resolveBundle` first, then approves any bundle URL the workspace has already loaded for the same CLAP ID.

```ts
import { openWorkspace } from "@audiorective/daw";
const workspace = await openWorkspace(context, file, {
  resolveBundle: ({ pluginId }) => (pluginId === "com.oxo.music.oxosynth2" ? "/plugin/oxo-synth2.wclap" : undefined),
});
```

### Device parameters

One row shape lists the parameters of a WebCLAP plug-in and of a built-in rack effect, and one method changes either, so an agent or an app does not tell them apart.

```ts
const rows = workspace.deviceParameters(device.id); // { id, name, kind, min, max, default, value, step?, unit?, text? }[], tracked
const cutoff = rows.find(({ name }) => name === "filter freq")!;
project.edit("Darker", () => project.setDeviceParameter(device.id, cutoff.id, 20)); // heard at once, one Undo step, saved
const slot = rackDeviceId(track.id, "lp"); // a built-in effect is "trackId:slotId": slot IDs are unique only inside a track
project.edit("Open the filter", () => project.setDeviceParameter(slot, "frequency", 4000)); // the data setTrackEffects writes
```

- **Rows.** `id` is the CLAP parameter ID as a string (a plug-in) or `enabled`, `wet`, `mode`, `frequency`, `q` (filter), `delayTime`, `feedback` (delay), `band<i>.frequency|gain|q` (equalizer). `min`, `max`, `default` and `value` are in the row's own units: a plug-in's native scale (its `text` shows what it means, `"+15 ct"`), a rack effect's `unit` (`"hertz"`, `"seconds"`, `"decibel"`, `"normalized"`). `step: 1` means whole numbers only. `text` is the plug-in's display string and appears while it describes `value`. `deviceParameters` is tracked: an effect that reads it re-runs on an edit and on a value the plug-in moves itself. It throws for an unknown device, and a plug-in no Workspace has loaded yet has no rows.
- **One authority.** A WebCLAP device's `parameters` table (`ProjectDevice.parameters`: id, name, range, default, value) holds the song's value of each parameter, and the table wins: after the Workspace loads the plug-in's `state` bytes it writes the table's values into the plug-in, so a value inside the bytes never disagrees with it. The table is filled from the plug-in's own report the first time a Workspace loads it (no Undo step, no new version) and again when the plug-in reports other parameters. `project.setDeviceState(id, bytes)` empties the table (the bytes carry their own values) and the Workspace refills it from what the plug-in then reports. `captureDeviceState` and the plug-in's own state refresh leave it alone.
- **Edits.** `project.setDeviceParameter` checks the value against the row (`min` to `max`; outside it throws, so a wrong unit stays visible) and, like a knob, snaps it to the nearest whole step counted from `min` when `step` is 1 (a tie goes up, so `53.9` applies as `54`); it returns the value applied. It joins the Undo step and version of the surrounding `project.edit` or `applyEdits`, like every Project edit method. The running Workspace writes the value into the plug-in without a rebuild; while audio runs, the host moves a smooth parameter to the new value over 20 ms as value events 32 frames apart (Undo and Redo do the same), so a plug-in without parameter smoothing does not step its sound; a parameter that is an enum or a stepped one with fewer than 128 values (a switch, a mode) jumps at once, and a stopped or offline context takes every value at once. A rack effect smooths through its own Params. Undo puts back only the parameters the step set (a value the plug-in moved by itself meanwhile stays); if the person turned the same parameter since, Undo is a `conflict`.
- **Rack effects.** The method writes the same Project data as `setTrackEffects` and refuses a parameter a rack macro drives (set the macro with `setTrackMacroValue`). Its Undo step records the parameter, not the whole rack: Undo puts back only that value and is a conflict only if that parameter changed since, not another parameter of the same track. A whole-rack `setTrackEffects` records the whole rack.
- **Plug-in changes.** A value the plug-in changes itself (its own automation, the person turning its GUI) is stored in the table without an Undo step or a new version. It is what `deviceParameters` reports and what `expectedValue` is compared against.
- **Agents.** `applyEdits` has the operation `setDeviceParameter { deviceId, parameterId, value, expectedValue? }`; a stepped row snaps `value` and `receipt.deviceParameters` (`[{ deviceId, parameterId, value }]`, one per such operation in request order) holds the value applied; a different current value (beyond a relative 1e-6, absolute 1e-9 near 0) is `conflict` naming it, and the MCP tool `read_device_params` returns the rows ([MCP](./mcp.md)).
- **Files.** `saveDawProject` writes the table as the `ClapPlugin`'s `Parameters`: one `RealParameter` per row with `parameterID` (the CLAP ID), `name`, `min`, `max`, `value` and `unit="linear"`, so other DAWs can read the values; the default and `step` (which `RealParameter` has no field for) go to the `audiorective/host.json` sidecar. `openDawProject` reads `RealParameter`, `IntegerParameter` and `BoolParameter` with a `parameterID` (a row it cannot read is skipped with one warning; a `RealParameter` with `unit="normalized"` is a 0..1 fraction that the Workspace maps into the plug-in's range when it loads, `linear` or no unit is the plug-in's own value, any other unit is skipped with one warning); without the sidecar a default is the value. The plug-in's own report replaces a table that does not match it when it loads. A file saved from the Workspace reopens with the same values heard. Bitwig Studio drops a `ClapPlugin` and the sidecar, so it shows none of this.

### Editing a running project

`Workspace` watches `project.cells.revision` (and the `project` setter). Edit `Project` directly and the change is heard; there is no commit step.

```typescript
const track = project.tracks[0]!;
const clip = track.clips[0]!;
project.setTempoChanges([{ beat: 4, bpm: 60 }]); // light edit: applied automatically
project.moveClip(clip.id, track.id, 2.5); // light edit

const bass = project.addTrack("Bass", "midi"); // structural edit: topology differs
workspace.cells.needsSync.value; // true once the runtime has noticed; transport keeps playing
if (workspace.cells.needsSync.value) await workspace.sync(); // rebuild hosts and routing, clears needsSync

await workspace.flush(); // resolves when pending automatic application is done; rejects if it failed
workspace.cells.error.value; // message of the latest failed application, or null
workspace.cells.warnings.value; // frozen array of non-fatal notices, tracked
```

**Light edits** keep the same tracks: tempo map, clips (including envelopes, fades, gain automation and warp or stretch), effect rack settings and macros, device state bytes, device parameter values, mixer (master volume, track volume, mute, solo, pan), volume automation, track routing and sends, adding or removing a bus track that hosts no device, and adding, removing or reordering the devices of a track that stays. They apply in place and hosts that stay stay loaded. A device change loads the new plug-ins off to the side, then rewires only that track's chain in one step while playback continues: the other tracks play on, the edited track crossfades from its old chain to the new one over 25 ms, and sounding notes on a MIDI track whose first device changed are ended. A removed plug-in's last state is kept in the Undo step that brings it back. A plug-in whose bundle cannot load is a warning and the track plays without it, as after `sync()`. Editing while playing is click-free: mixer, send and effect-rack changes ramp over about 10 ms, and a clip edit under the playhead (move, trim, split, source range) crossfades over 12 ms from a shared cut time, so shifting audio by whole periods is inaudible. A clip trimmed to the playhead and a seek while playing fade the same way, and a device change on a playing track crossfades from the old chain to the new over 25 ms. A clip's own start and end stay hard cuts unless the clip has a fade. A channel pans a mono input with the equal-power law (about -3 dB per side at centre) and a stereo input with the stereo law, which plays the same signal 1.41 times louder at centre (2 times at the sides); the input follows the widest connection. When a device change turns a mono audio track stereo (its first plug-in, with only mono clips and no rack effects) or back, the track crosses between two ways into the strip, one per law, with gains scheduled ahead of time, so the level glides over the 25 ms crossfade and no graph edit is ever heard (the way is changed only while its gain is 0). The final level rule is the law's: a track with a plug-in, a rack effect or a stereo clip pans with the stereo law, a track of mono clips alone with the mono law. A track the project does not describe (an instrument sound, a bus) is asked what its sources carry (a probe in the audio graph) just before the swap and the last answer is kept, so the same switch applies; if nothing was sounding to measure, it plays the plain crossfade. Device changes made while a width switch is still under way (about 0.15 s) also play the plain crossfade. The timers that dispose a replaced plug-in or sampler wait on the audio clock, not the wall clock, so a busy machine cannot cut a note before its fade ends. Clip edits use a 40 ms lead before the cut (`playbackLead`), device changes 25 ms. Splitting a clip under the playhead crossfades like any other clip edit: the second half joins the 12 ms ramp at the level the seam is at, so the old source and the two halves always add up to one. Moving a playing MIDI clip keeps the notes that still sound at the playhead at the same pitch (they end where the moved note ends), ends the ones the new place no longer covers with their normal release, and starts notes the new place newly covers. A MIDI note edit ends only the sounding notes it changed or removed; a note it re-pitches or moves so that it still covers the playhead starts again at once at its new pitch with its own velocity and ends where the note ends. Clip edits stay click-free at any rate, such as a 60 Hz drag: a source cut while it is still fading in or out falls on from its current level instead of jumping. Edits coalesce: any number of edits in one synchronous burst cause one application in the next microtask. Applications never overlap. Device-state restore is asynchronous, so edits that arrive during one queue exactly one more application that reads the latest `Project`.

**Structural edits** add, remove or retype tracks (a bus without devices is a light edit). `sync()` stops transport, captures live plug-in state, reloads WebCLAP hosts and rebuilds routing; it is slow, asynchronous, can fail and interrupts sound. For that reason the workspace never runs it by itself. It sets the read-only `workspace.cells.needsSync` and leaves transport and hosts untouched, so the UI can offer a rebuild action at a moment the user accepts a glitch. `sync()` clears `needsSync` and applies everything in `Project`, including light edits made meanwhile. While `needsSync` is true the other light edits (clips, tempo, routing, devices) wait for `sync()`, or take effect if the topology is restored first; only the mixer (master volume, track volume, mute, solo, pan) and the effect rack and macros of tracks that are already loaded keep following the Project, so a fader never freezes while a rebuild is pending.

`workspace.cells.error` is a read-only cell holding the message of the latest failed automatic application (for example a plug-in rejecting saved state), or `null`. The next successful application or `sync()` clears it. Failures never become unhandled rejections. Edit again or call `sync()` to retry application. A media read failure publishes one error per clip in this cell. An audio fallback export rejects and aborts its destination when its render cannot read a clip's media.

`await workspace.flush()` resolves when all pending automatic application has finished and rejects with the latest failure. `checkpoint()` (and so `saveWorkspace()` and `saveWorkspaceTo()`) and `exportAudioFallbackTo(workspace, …)` wait for pending application first, but do not reject because of an earlier failure: `Project` is the document. After `dispose()` the watcher is disposed, pending applications are dropped, and `flush()` resolves without error.

Edits the runtime makes itself, such as capturing plug-in state into `Project` during `sync()` or `save()`, are marked as already applied, so they cause no second application. Callers never need to refresh the runtime after an edit: light edits propagate by themselves, and `sync()` is the one explicit operation, for a structural change reported by `cells.needsSync`.

### Mount playback controls

Pass `workspace.player` directly to `mountPlayer` for play, pause and seeking. Its seek bar follows the project duration in seconds, including clip and tempo edits. Programmatic seeks and stops update the view even while paused.

```typescript
import { openWorkspace } from "@audiorective/daw";
import { mountPlayer } from "@audiorective/widgets/player";

const options = { destination: context.destination }; // Route to speakers in this app.
const workspace = await openWorkspace(context, file, options);
const controls = mountPlayer(container, { player: workspace.player });

// On teardown or before mounting controls for another Workspace:
controls.dispose();
workspace.dispose(); // also disposes the project it opened
```

The same view works with `Workspace.create()` and `openWorkspace()`. Pass a `destination` in all three paths for audible output, or connect `workspace.output` to your own graph. The widget borrows the transport. Your app still decides when to stop playback at the end or loop a region.

## Runtime internals

`Workspace` is a facade over small internal modules; none is part of the `daw/runtime` surface except what `Workspace` re-exports. A collaborator receives a narrow handle (a function returning the current `Project`, the shared track-runtime map, an `isDisposed` check) and never imports `Workspace`. Project stays the only owner of persistent data. The only collaborator write is a prepared stretch the caller applies in its own undo transaction, and observable state stays in `Workspace.cells`.

| Module                                  | Owns                                                                                                                                                                             | Reads                                                     |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `runtime.ts` (`Workspace`)              | The public API, the `cells`, the track-runtime map, the graph build, transport (`play`, `pause`, `stop`, `seek`), and Project-edit reconciliation (`flush`, `sync`, light edits) | Everything below, through narrow handles                  |
| `mixer.ts` (`Mixer`)                    | The `Channel` and `SendBus` strips, send routing, and writing Project mixer values into them                                                                                     | The track map, the current Project, the master `GainNode` |
| `clip-scheduler.ts` (`ClipScheduler`)   | Scheduled audio handles, media chunk loading, decoded-buffer caches, one tick window of MIDI and audio clips                                                                     | Track runtimes and timing passed per call                 |
| `audition.ts` (`Audition`)              | The current clip or range audition cell and the clock or handle that plays it                                                                                                    | The current Project, the scheduler, the master output     |
| `clip-stretch.ts` (`ClipStretch`)       | One cancellable stretch job per clip and the prepared edit it returns                                                                                                            | The current Project                                       |
| `take-placement.ts`                     | Pure take-anchor validation and take-position maths                                                                                                                              | Nothing                                                   |
| `track-reconcile.ts`                    | Pure diffs between a live track and its Project track (rack settings, gain-automation-only edits, device keys)                                                                   | Nothing                                                   |
| `track-runtime.ts`, `project-lookup.ts` | The shared `TrackRuntime` type and a clip lookup by id                                                                                                                           | Nothing                                                   |

## Step Sequencer

`workspace.transport` is the Workspace's Clock: `transport.timeline`, `transport.attach(scheduler)` and `transport.refresh()` let any scheduler, such as an `@audiorective/sequencer` `Sequencer` created with `{ transport: workspace.transport, context: workspace.context }`, follow Workspace's beats and tempo. Pause, stop and seek reset attached schedulers; Workspace keeps play, pause, seek and tempo.

Attach a caller-owned `StepSequencer` with `workspace.transport.attach(seq)`. Route each lane's `output` (or your `onHit` voices) to a caller-selected mix path. The attached sequencer uses Workspace's Clock windows and tempo mapping. Edits to its lanes and steps re-queue pending hits, and transport pause, stop and seek reset its scheduled events. Call the returned detach function (or `seq.dispose()`) to remove only this sequencer. An attached live pattern belongs to the current app session. Saveable Arrangement clips belong to Project.

## Session scenes and clip slots

The Session grid is part of the song, apart from the Arrangement: an ordered list of scenes and, for each scene and track, a slot holding at most one clip that is not on the timeline. `sessionFor(project)` (from `@audiorective/daw/project` or the root) returns the one `ProjectSession` of a Project. Unlike `selectionFor`, it is song content: saved in the file, undoable inside `project.edit` and part of `project.cells.version`.

```ts
import { sessionFor } from "@audiorective/daw/project";

const keys = project.addTrack("Keys", "midi");
const vocal = project.addTrack("Vocal", "audio");
const sampleRate = 48000;
const pcm = new Float32Array(sampleRate);
const session = sessionFor(project);
const verse = session.addScene({ name: "Verse" });
const chorus = session.addScene({ name: "Chorus", afterSceneId: verse.id });
const slot = { trackId: keys.id, sceneId: verse.id };
const clip = session.setMidiClip(slot, { notes: [{ pitch: 60, velocity: 1, start: 0, duration: 1 }], duration: 4 }, { name: "Chords" });
session.setAudioClip({ trackId: vocal.id, sceneId: verse.id }, { sampleRate, channels: [pcm] });
session.duplicateScene(verse.id); // copies every slot clip, right after Verse
session.moveClip(slot, { trackId: keys.id, sceneId: chorus.id }); // same kind of track; replaces the target's clip
session.copyToArrangement(slot, { atBeat: 16 }); // a copy on the timeline; the slot keeps its clip
session.copyToArrangement(slot, { atBeat: 32, linked: true }); // same, but sharing the slot clip's notes
session.copyToSlot(clip.id, { trackId: keys.id, sceneId: chorus.id }, { linked: true }); // a linked copy of any timeline or slot clip, in a slot
```

- `session.scenes` (tracked) lists `{ id, name }` in order; `clipAt({ trackId, sceneId })` (tracked) returns the slot's clip or `null`, also for an unknown scene or track. `midiClipAt(slot)` and `audioClipAt(slot)` return the same clip already typed as `MidiClip` or `AudioClip`, and `null` when the slot is empty or holds the other kind, so `session.midiClipAt(slot)?.midi.edit(...)` needs no cast.
- `addScene({ name?, afterSceneId? })`, `renameScene`, `removeScene` (drops the scene's clips), `moveScene(sceneId, index)` (puts the scene at that position and keeps its clips; the same position is no change) and `duplicateScene(sceneId, { afterSceneId? })` (the copy is named "… copy" and has new clip ids).
- `setMidiClip(slot, data, { name? })` takes what `addMidiClip` takes; `setAudioClip(slot, audio, { name? })` what `addAudioClip` takes. Each replaces the slot's clip. `moveClip(from, to)` keeps the clip's id; `clearSlot(slot)` empties a slot.
- `copyToArrangement(slot, { trackId?, atBeat? | atSeconds?, linked? })` needs exactly one position, in the unit you prefer (the tempo map converts), and a track of the clip's kind (default: the slot's track). `linked: true` makes a MIDI copy that shares the slot clip's notes.
- `copyToSlot(clipId, slot, { linked? })` puts a copy of a timeline or slot clip in a slot of a track of the same kind, replacing what it held; the source stays. With `linked: true` a MIDI copy shares the source's notes and events, so an edit through any member (slot or timeline) changes all of them, live, as one Undo step. `makeClipUnique`, `clearSlot` and `removeScene` leave the rest of a group linked; `duplicateScene` copies are independent. Slot clips of a group on different tracks each play into their own track's instrument. See [Linked clips](#linked-clips).
- A slot clip is an ordinary `ProjectClip` whose `time` is 0. **Works on slot clips by id:** `setClipLoop`, `resizeClip` (the clip keeps `time` 0), `setClipSourceRange`, `setClipName` and `clipName`, `setAudioClipEnvelope`, `setAudioClipGainAutomation`, `applyAudioClipStretch`, `clip.midi.edit` and the `setClipName` and `editNotes` edits of `applyEdits`. **Timeline only, never touching slot clips:** `moveClip`, `duplicateClip`, `splitClip`, `removeClip` (use `clearSlot`), `rippleDelete`, `findClips`, `overview().tracks` (slot clips are in `overview().session`) and the `copyRange` and `moveClip` edits. `auditionAudioClip` takes slot clips too.
- Every session edit inside `project.edit` joins that Undo step, including note edits in a slot clip; each one advances `project.cells.version`. `project.snapshot()` copies the grid, and removing a track removes its slots.
- Errors: an unknown scene or track throws `RangeError("Project session has no scene or track with that id.")`; a clip that does not fit its track's kind (a MIDI clip on an audio or bus track, or `moveClip` and `copyToArrangement` across kinds) throws `RangeError("Project session slot clip must match its track kind.")`.

DAWproject saves it as `<Scenes>` after `<Arrangement>` (clips that share notes with another clip, on the timeline or in a slot, are written once and the others as `reference`): one `<Scene id name>` with a `<Lanes>` holding a `<ClipSlot track="…">` for each filled slot, whose `<Clip>` is written exactly like an arrangement clip (audio windows, loops and shared recordings included). An empty slot is no `ClipSlot`, so scenes without clips stay valid. A file without `<Scenes>` opens with no scenes.

## Clip Launcher

`workspace.cells.session` is a [`ClipLauncher`](./launcher.md) over the Project's audio and MIDI tracks, built from `sessionFor(project)`, as a cell: `session.value.tracks[trackId].clips[i]` is the Session clip of scene `i` on that track, `null` for an empty slot, a file-backed audio clip or a MIDI clip on a track with neither a device nor an [`instruments`](#page-made-instruments) entry, and `session.value.launchScene(i)` launches scene `i`. The launcher is made with `emptySlots: "stop"`, so launching a scene (or each entry of `playChain`) stops the tracks whose slot in that scene is empty, on the scene's boundary; a `launchScene([clipA, clipB])` clip list leaves other tracks alone. Adding, duplicating, renaming, moving or removing a scene changes the launcher in place (`insertScene`, `removeScene`, `moveScene`, scene names): clips in other scenes keep playing, a launch already waiting keeps its clips and `clip.index` follows the move; only a clip in a removed scene stops. Other edits replace only the clips they change. A file-backed audio slot clip (what a file opened with `openWorkspace` from a Blob holds) has no launcher clip until its audio has been read into memory, then `session.value.tracks[t].clips[i]` and `sessionClip` fill in (tracked readers re-run). That copy costs memory: the clip's window, or the whole recording when the clip loops, as 32-bit floats per channel, plus the launcher's own buffer. A MIDI Session clip loops over its length through the track's first device or its instrument; notes still sounding are released when the track changes clip, stops or returns to Arrangement, and that track's Arrangement MIDI is not sent while a Session clip holds it. Non-note MIDI events in a clip are not sent from Session. `workspace.sessionClip(trackId, clipId)` finds the launcher clip of a slot clip by its ID (a tracked reader; a timeline clip has none, and a file-backed one has none until its audio is read). Launch with the launcher's own commands: `workspace.sessionClip(t, c).launch({ quantize: "4n" })`, `session.value.launchScene([clipA, clipB])` (one boundary for every listed track), `session.value.tracks[t].stop()` (back to Arrangement), `session.value.cancelQueued()`, and read `session.value.playing`, `queued` and each clip's cells. The launcher's [`quantize` cell](./launcher.md#layer-1-tracks-of-buffers) defaults to a bar of the Project's time signature; set it to `"4n"` for a beat or `"none"` for now.

A launched clip plays through the track's devices, inserts and mixer (it is the launcher track's output connected to the track input) and takes that track away from Arrangement until it is stopped or a one-shot ends. Tracks that are not launched keep playing as before. Audio Session clips loop at their original sample rate and length and keep their recorded speed (`warp: false`); `clip.configure({ loop: false })` makes one a one-shot that returns the track to Arrangement at its exact audio end. A Session clip sends its controllers, pitch bend, program changes and pressure as the Arrangement does for the same content: the values before the clip's window (its loop, for a looped clip) are carried to the start of every pass, and a pedal still down at a pass end is released there. When the clip stops, is replaced, or the transport stops or pauses, each performance controller it moved goes back to rest (pedal up, bend centre; the curated list in [MIDI](midi.md)), unless a later clip took it over; a seek chases the new position instead, so a pedal held on both sides is not lifted.

An app that only plays Session clips, such as a groovebox whose scenes are `sessionFor(project)` scenes, sets `workspace.arrangement.value = false` (or `arrangement: false` when creating or opening the Workspace): the timeline is not played, so a track with nothing launched is silent and clip positions are never heard. It can be switched while playing; off releases Arrangement sound at once. `session.value.playChain([0, 0, 1, 2])` plays scenes back to back for their lengths and then stops (see [Song chains](./launcher.md#song-chains)).

The launcher follows `workspace.transport`: a launch made while stopped waits for `play()`, Pause freezes it and Play starts fresh (clips are silent, waiting launches keep their place), Stop and Seek clear it, a tempo change moves waiting boundaries with the beat and keeps playing clips going. Session edits (and clip edits, which the running Workspace applies by itself) replace the Session clips to match, and a Session clip whose slot clip is replaced or cleared is stopped at once. `sync()` (a structural rebuild) replaces the launcher, so read `workspace.cells.session.value` inside the effect that uses it. The launcher is built the first time `session` or `sessionClip` is read (an app that never launches clips never copies their audio), and a clip's audio is read when the launcher is built or the clip is replaced. DAWproject stores the Arrangement, the scenes with their slot clips, and media; what is launched or queued is runtime state and is not saved. File-backed media plays only in the Arrangement.

```ts
import { mountClipGrid } from "@audiorective/widgets";

import type { ProjectClip, ProjectTrack } from "@audiorective/daw/project";

declare const drums: ProjectTrack, bass: ProjectTrack; // tracks that hold Session clips
declare const drumsClip: ProjectClip, bassClip: ProjectClip;
declare function showError(error: unknown): void;
const session = workspace.cells.session.value;
const verseDrums = workspace.sessionClip(drums.id, drumsClip.id)!;
const verseBass = workspace.sessionClip(bass.id, bassClip.id)!;
session.quantize.value = "4n";
const grid = mountClipGrid(root, {
  launcher: session,
  launch: async (command) => {
    try {
      await workspace.play(); // a launch made while stopped would wait for play
      command();
    } catch (error) {
      showError(error);
    }
  },
});
grid.setLayout({
  tracks: [
    { track: session.tracks[drums.id]!, label: "Drums" },
    { track: session.tracks[bass.id]!, label: "Bass" },
  ],
  scenes: [
    {
      label: "Verse",
      clips: [
        { track: session.tracks[drums.id]!, clip: verseDrums, label: "Drum loop" },
        { track: session.tracks[bass.id]!, clip: verseBass, label: "Bass loop" },
      ],
    },
  ],
});
// Tear down the DOM view while leaving the borrowed Workspace available.
grid.dispose();
```

## Effect rack

`ProjectTrack.effects` is the ordered snapshot of built-in inserts (Filter, PingPongDelay and Equalizer slots). The track's runtime rack is a data-driven layer over an [`EffectChain`](./effects.md#effectchain): it owns its effects, keeps processors with the same slot ID and type across edits, and reorders, adds and removes them with the chain's click-free crossfades. An empty rack passes audio through. Bypass (`enabled: false`) sets the effective mix to dry while preserving the configured mix. Filter accepts lowpass or highpass, 20–20,000 Hz and Q 0.1–20. Delay accepts 0.01–1 second and feedback 0–0.95. Both accept a mix from 0–1. An EQ slot is `{ id, type: "eq", enabled, wet, bands }`; each band uses `{ frequency, gain, q }` and follows the [Equalizer ranges](./effects.md#parametric-equalizer), and edits retain a slot's Equalizer when its band count stays the same.

```typescript
const track = project.addTrack("Lead", "midi");
project.setTrackEffects(track.id, [
  { id: "filter", type: "filter", enabled: true, wet: 1, mode: "lowpass", frequency: 1200, q: 0.7 },
  { id: "delay", type: "delay", enabled: true, wet: 0.35, delayTime: 0.25, feedback: 0.25 },
]);
```

Use `project.setTrackEffects(trackId, slots)` for headless project edits and await `workspace.flush()` when you need to wait for the rack to reflect that edit. A running Workspace applies the edit to the rack in the task turn that made it, preserving transport and loaded WebCLAP hosts. The signal runs from the track's source through its hosted devices, then the rack, then the mixer. `workspace.trackEffectOutput(trackId)` borrows the rack's pre-mixer output for an analyser. Disconnect only the analyser you connected, or remount it if a structural edit rebuilt that track.

`project.setTrackRackPreset(trackId, { effects, macros })` replaces a track's insert setup and macro settings in one edit. Macro settings are in `track.effectMacros` (see [Rack macros](#rack-macros)). Await `workspace.flush()` after structural rack edits. Bind a UI knob to `workspace.trackMacroValue(trackId, macroId)` for reads and `project.setTrackMacroValue(trackId, macroId, value)` for edits: a running Workspace moves the native macro timeline and every mapped parameter on the audio thread in the task turn that made the edit, without stopping transport. Project archives preserve mappings and positions in Audiorective metadata. The rendered audio fallback carries the audible settings to other DAWs.

The DAW's Devices panel inserts, adjusts, bypasses, reorders and removes Filter, Delay and EQ slots. DAWproject uses vendor-specific `BuiltinDevice` entries in order and versioned JSON settings in `plugins/`. Open the project in Audiorective to edit the inserts. Use the audio fallback when sharing the processed sound with another DAW.

Use `workspace.trackEffectOutput(trackId)` to connect a borrowed spectrum analyser. Use `workspace.trackFilterResponse(trackId, slotId, frequencies, magnitudes, phases)` to draw the live response for a Filter or Equalizer slot. Apply editor mutations with `setTrackEffects()` so the controls, audio and saved settings share one owner.

### Rack macros

Each macro owns one normalized control and one or more built-in parameter targets. Set its mappings in a complete preset.

```typescript
const track = project.tracks[0]!;
project.setTrackRackPreset(track.id, {
  effects: track.effects,
  macros: [
    {
      id: "tone",
      label: "Tone",
      value: 0.5,
      targets: [
        { slotId: "filter", parameter: "frequency", min: 200, max: 8000, scale: "exponential" },
        { slotId: "delay", parameter: "feedback", min: 0.05, max: 0.65 },
      ],
    },
  ],
});
await workspace.flush();
workspace.trackMacroValue(track.id, "tone")!.value; // bind a knob here
project.setTrackMacroValue(track.id, "tone", 0.7);
```

Writing a macro moves the native macro timeline and every mapped target together, and its value is what the Project keeps. The control stays valid across `setTrackEffects`. For audio-clock automation, pass `workspace.trackMacroAutomation(trackId, macroId)` to [AutomationBinding](./automation.md). Linear or hold segments in the normalized curve produce native ramps or steps on the mapped parameters. Exponential targets require positive endpoints. Stop a running binding before taking manual control so subsequent curve edits do not reprogram the target.

Only one macro can own a given slot parameter. Use `rackMacroRange(slot, parameter)` (from `@audiorective/daw/project`) for ranges. Supported targets are mix (`wet`) on every insert, Filter `frequency` and `q`, and Delay `delayTime` and `feedback`. Removing a slot drops its mappings. Bypassing a slot keeps its macro phase and makes that insert dry.

A preset carries version 1, the ordered slots, mappings and current macro positions. Authored curves belong to their caller. A successful recall resets the recalled positions and cancels their old schedules. Existing controls retain identity when their IDs and labels match.

### MIDI controller lanes

A MIDI track can carry controller movement of its own, beside its clips: `track.controllerLanes` is a list of `ControllerLane`, one per `(expression, channel, controller)`, and it plays in Arrangement (a Session clip sends its own clip events, not the track's lanes). Use a lane for what changes over the song (a sustain pedal, a mod wheel, pitch bend, channel pressure) and clip `events` for what belongs to one clip.

```typescript
const track = project.addTrack("Piano", "midi");
project.setControllerLane(track.id, {
  expression: "channelController", // or "pitchBend", "channelPressure", "polyPressure", "programChange"
  channel: 0, // 0 to 15
  controller: 64, // the controller number; the key for polyPressure; 0 otherwise
  points: [
    { time: 0, value: 0, shape: "hold" }, // beats from the start of the song
    { time: 4, value: 127, shape: "hold" }, // pedal down at beat 4
    { time: 8, value: 0, shape: "hold" },
  ],
});
```

- **Units.** `time` is in project beats (0 or more). `value` is an integer in the controller's own range: 0 to 127 for a controller number, channel pressure, poly pressure and program number, and 0 to 16383 for `pitchBend` (centre 8192). `shape` is how the value goes on to the next point: `"linear"` moves toward it, `"hold"` keeps this value until it. Two points at one time are a step (every one is sent, in order); a program-change lane always steps. A controller number from 120 up (channel-mode messages) is not a lane.
- **`setControllerLane(trackId, lane)`** replaces one lane; an empty `points` removes it. It is an undoable edit like `setVolumeAutomation`, part of the Project version, and `applyEdits` has the same operation (`setControllerLane`, positions as `atBeat` or `atSeconds`). `read_project` lists each lane and `read_automation` returns one in the rows the operation takes ([MCP](./mcp.md)). `rippleDelete` and an inserting `copyRange` move lanes with the song.
- **Playback.** A running Workspace sends each lane to the track's first device or `instruments` sampler as MIDI messages: a message at every point, and along a linear segment one at each 1/32 beat (15.6 ms at 120 BPM) where the rounded value differs from the last one sent, so a ramp of 127 steps over four beats is at most 127 messages. A hold segment sends nothing between its points. A run that **begins** (a start, a seek, a loop wrap, the arrangement switched back on, a loop edit) **chases the position**: for each device it works out the state the beat needs from every source (the clips' events before it within each clip's window and loop, with the values before the window carried to its start, the track lanes (a lane's value in force at that beat, or, before its first point, the controller's **rest value**), program changes and bank select (CC0, CC32)), and sends the controllers that differ from what the device was last sent: the value the position needs for every controller something set, and the rest value for a performance controller playback had moved that nothing at the position drives. A controller the device already holds at that value is not sent again, so a pedal held on both sides of a seek does not dip (a sampler lifts its pedal on all-notes-off, so it is pressed again, never lifted). The messages go before the segment's own at that time, a bank select before its program change, and live, `renderMixRange`, `renderStems` and `exportAudioFallbackTo` send the same list for the same start position (a fresh device gets every needed value), so a seek to bar 9 sounds the volume and pan the song set at bar 1, as the offline render does. **Only a curated list of performance controllers rests** (`controllerRestValue`): 8192 for pitch bend, 0 for pressure, 100 for volume (7), 64 for pan (10), balance (8) and the sound controllers 71 to 74, 127 for expression (11), 0 for modulation (1), breath (2), foot (4) and the pedals 64 to 69; nothing for a program lane. Bank select (0, 32), data entry (6, 38), data increment and decrement (96, 97), NRPN and RPN selectors (98 to 101) and every other controller are never reset and are chased by their own value only, so a stop does not turn a file's pitch-bend range of 12 semitones into 0. **Stop and pause** put back every performance controller playback moved off rest, from lanes and from clip events alike: the pedal up, pitch bend at centre, pressure and the others at their rest value; a **seek** does not reset first, because the run it starts chases the new position (a program change has no rest and stays). **At one time** a track's messages play in this order: note-offs, program changes, controllers and pitch bend, note-ons. `renderMixRange`, `renderStems` and `exportAudioFallbackTo` send the same messages as the live transport. An edit to a lane while playing refills the look-ahead from the new lane; a value already sent stays until the next message.
- **Lane over clip.** A track lane replaces the clips' own events for the same `(expression, channel, controller)` in Arrangement playback, offline renders and `exportMidiFile` (the rule a DAW applies to an automation lane over clip content): while the lane exists, those clip events are not played or exported. Clip events for a controller with no lane play as before. While a Session clip holds the track, the track's lanes and the Arrangement clips' events do not reach the device; the Session clip sends its own controllers, and a pedal or bend the Arrangement had moved is put back at rest when playback stops or pauses.
- **Reading lanes.** `read_project` and `read_automation` show `controller` only for `channelController` (the controller number) and `polyPressure` (the key); for the other expressions it is left out, as `setControllerLane` takes none there, so the rows read can be sent back unchanged. Undo of a lane edit is recorded per lane: a later change to another lane of the track does not block it, a later change to the same lane does (`conflict`). `rippleDelete` and an inserting `copyRange` keep each ramp's values outside the range.
- **MIDI file.** `exportMidiFile` writes the sampled messages into the track, merged with the clip events by beat, the lane's messages first at one beat. `importMidiFile` keeps controllers as clip events.
- **`.dawproject`.** A lane is a `Points` with `unit="normalized"` beside the track's `Clips`, in beats, the form Bitwig Studio writes; values are `value / 127` (or `/ 16383` for pitch bend) and read back with `round(normalized × max)`, exact for every integer. A point's `interpolation` in the file says how the value arrives there from the previous point, so the codec shifts the model's `shape` by one point. Clip events are written inside the MIDI clip as `RealPoint` with `unit="normalized"` and `interpolation="hold"`. See [DAWproject support](./dawproject-support.md).

## Exchange with other DAWs

Four functions move material in and out as plain files. None reads a `File` itself or starts a download: pass bytes (`new Uint8Array(await file.arrayBuffer())`) and hand the result to your own save code.

### MIDI files

`importMidiFile(project, bytes, { tempo? })` (pure, `@audiorective/daw/project`) adds the tracks of a Standard MIDI File (format 0 or 1, PPQ division) to the Project as **one undoable edit**, labelled `Import MIDI file`. Each file track with notes or controller moves becomes a MIDI track named from its track-name meta event (`Track N` without one), holding one clip at beat 0 that ends on the first bar line at or after the track's content. The tempo-only conductor track becomes no track. It returns `{ tracks, tempoMapUsed, warnings }`.

- **Channels** stay on the notes (`note.channel`, 0-15; GM drums are channel index 9). A track that mixes channels stays one track and gets a warning.
- **Controllers** (sustain pedal, mod wheel), pitch bend, program changes and pressure go into the clip as events with their raw bytes and play back with the clip.
- **Tempo and meter.** `tempo: "file"` (default) replaces the song's tempo changes and time signatures with the file's; ticks convert to beats exactly (a beat is a quarter note at any PPQ), and what the file leaves out defaults to the MIDI defaults (120 BPM, 4/4). `tempo: "song"` keeps the song's maps and places the notes at the same beats, so they play at the song's tempo. A file with neither tempo nor signature events leaves the song's. `tempoMapUsed` says which one applies: `"file"` or `"song"`.
- **Not imported:** sysex, text and lyric meta events, key signatures, SMPTE time division and format 2 (these throw or are skipped). A file that is not an SMF throws `Invalid MIDI file.`

`exportMidiFile(project, { ppq?, runningStatus? })` (pure) returns a format 1 SMF as `Uint8Array`: the first track holds the title, tempo changes and time signatures, then one track per **MIDI track** (audio and bus tracks are not exported) with its **timeline** clips played out as the Workspace plays them: windows, loops and linked clips are expanded, notes cut at clip edges, channels, pedal, controllers, pitch bend and program changes kept, and the track's [controller lanes](#midi-controller-lanes) sampled in as playback sends them. PPQ is 960 by default (an integer 1-32767); beats round to ticks, and a note that would round to zero length is one tick long. Session slot clips, volume, pan, mute and devices are not exported, and the file always carries the **song's** tempo and meter map. The low-level pieces are `parseMidi` (now with per-track data) and `writeMidi` in [MIDI](./midi.md#midi-files).

```typescript
import { exportMidiFile, importMidiFile } from "@audiorective/daw/project";

const { tracks, tempoMapUsed, warnings } = importMidiFile(project, new Uint8Array(await file.arrayBuffer()));
// project.undo() removes the tracks and restores the tempo map in one step.
const blob = new Blob([exportMidiFile(project)], { type: "audio/midi" });
```

### Audio files in

`await importAudioFiles(workspace, files, { atBeat? })` (`@audiorective/daw/runtime`) takes `Blob`, `File` or `{ name, bytes }` entries and returns `{ tracks, sampleRate }`. Each file becomes one audio track and one clip, named after the file without its extension, all at `atBeat` (default 0), as **one undoable edit** (`Import audio files`). WAV files are read directly (8/16/24/32-bit integer, 32/64-bit float, any channel count); other formats go through the browser's decoder, which resamples to the Workspace's rate itself. Every file is then resampled to the Workspace's sample rate with core's `resamplePCM`, frame 0 to frame 0: leading silence is kept, files that start together stay together, and a 44.1 kHz and a 48 kHz file of the same length end up with the same number of frames, so a click at one second is the same sample in both and nothing drifts over a long song. `resamplePCM` is a deterministic Kaiser-windowed sinc (about -90 dB aliasing, no linear-interpolation loss of high frequencies), so a 4-minute stereo file takes a couple of seconds on the main thread; open the Workspace at the file's rate to skip resampling.

Adding tracks makes the Workspace report `cells.needsSync`; run `await workspace.sync()` before playing, as for any track change.

### Stems out

`await renderStems(workspace, { range?, tailSeconds?, includeMix?, expectedVersion?, signal? })` renders every audio and MIDI track to PCM of its own and the full mix, offline, without touching playback or the song:

```typescript
import { encodeWav } from "@audiorective/daw";
import { renderStems } from "@audiorective/daw/runtime";

declare function save(name: string, blob: Blob): void; // your download helper
const result = await renderStems(workspace, { tailSeconds: 3 });
if (result.status === "rendered") for (const { name, audio } of result.stems) save(`${name}.wav`, encodeWav(audio, { bitDepth: 24 })); // result.mix, result.sampleRate, result.durationSeconds
```

All stems and the mix start at the same frame and have the same length: `range` (default from 0 to the end of the last clip) plus `tailSeconds` (default 2) for reverbs and delays. A stem is **the track alone through its own chain**: clips, volume and volume automation, pan, inserts, devices and instruments, then on through the bus it outputs to (so a submix bus's processing and the master volume are in it). **Sends are not in a stem**: send returns (effect buses) exist only in `mix`, which is rendered as heard, with mute, solo, sends and buses. Bus tracks have no stem. A muted track, or a MIDI track with no device and no `instruments` entry, has a silent stem of the same length (it is listed, so the file set is complete); `result.warnings` holds one sentence for each, for example `Track "Keys" has no instrument or plug-in, so its stem is silent.`, so report them to the person. Solo is ignored for stems. Because buses and sends are shared, the stems add up to the mix only when no send, effect bus or non-linear master or bus processing is involved. `expectedVersion` returns `{ status: "conflict" }` for a moved project.

## File contents and fidelity

The ZIP contains standard `project.xml` (Arrangement, and `Scenes` when the song has scenes), `metadata.xml`, `audio/*.wav` and, for WebCLAP devices, `plugins/*.bin`. Standard XML holds track/channel structure, `ClapPlugin` identity and `State` references, clip positions, notes, controller points, initial tempo and optional beat-based step-tempo automation, time signature, volume automation, arrangement markers, and channel mute/pan/solo. `audiorective/host.json` maps a CLAP device to a WebCLAP bundle URL; this is an Audiorective locator, not a portable DAWProject property. `audiorective/state.json` holds note IDs, the next generated project ID and the original ordered MIDI messages. Its fingerprint covers the clip's unit and standard note/control content; the MIDI details of a version 1 or 2 sidecar never attach to a clip, so such a file opens from standard XML with a warning (its audio details still apply). Its `version` is also the format marker for a point's `interpolation`: below 4 it is the model's `shape` (how the value leaves the point, written by earlier builds for volume automation and clip gain), and from 4, like in a file with no sidecar or from another application, it is how the value arrives at the point (Bitwig Studio's meaning); a file of an earlier version whose `Application` is Audiorective is converted when opened, and a save always writes version 4. If another application changes that content or removes the private entry, `openDawProject` rebuilds from standard XML and returns a warning. Audio sidecar data follows the XML audio ID and asset path, so reordering clips keeps gain and ID attached to the original audio.

For plug-in round trips, use `saveWorkspace(workspace)` to capture the live patch. The portable part of DAWProject is the CLAP ID and state bytes; `audiorective/host.json` is the private lookup needed to find browser `module.wasm`. Another DAW needs its own matching CLAP binary, and may drop the private bundle locator when saving.

Call `portabilityReport(workspace.project, workspace.cells.warnings.value)` (from `@audiorective/daw/dawproject`; a pure function of `Project`, so it also runs in Node with `portabilityReport(project)`) before sharing. It lists content represented in standard DAWproject fields, required CLAP IDs and limitations; it does not claim that a particular DAW has passed import testing. For an audible companion, call `await exportAudioFallbackTo(workspace, writableStream, { tailSeconds: 1, signal, onProgress })` (from `@audiorective/daw/runtime`). It renders a separate runtime offline from project time zero, writing a ZIP with `mix.wav`, per-track post-mixer `tracks/<id>.wav` and `manifest.json`. The render runs on an `OfflineAudioContext` in steps of the transport's tick interval; between steps it waits for file-backed media chunks and device messages and for the OPFS writer to catch up, so main-thread work, a slow media read or the live context's state cannot drop or delay frames, and the same project exports the same samples. It can finish faster or slower than the project's length. The mix includes hosted WebCLAP instruments and effects; the source project and its playback keep running. Captured PCM is temporarily stored in browser OPFS and removed after export; the offline context itself holds one channel of the whole render (about 11.5 MB per minute at 48 kHz). The export rejects unresolved devices, missing frames, cancellation, an offline render the browser cannot allocate and storage failures instead of delivering a knowingly incomplete backup. A project with more than 15 tracks exports the full mix without stems because one recorder supports at most 32 packed channels. The demo offers **分享說明** and **匯出音訊** next to **儲存工程**. This ZIP is a companion audio delivery, not a second DAWproject or an editable plug-in replacement.

`Project.snapshot()` supplies the export runtime with independent MIDI and in-memory PCM clip data plus copied device state. File-backed `AudioMedia` stays borrowed; retain it until the export settles.

`openDawProject` and `openDawProjectBlob` open files this package wrote and files other applications wrote. The model carries regular tracks, submix and effects buses, post-fader sends, second-based audio and beats- or seconds-based MIDI clips (seconds convert to beats on open) with windows, loops and fades, linked MIDI clips, CLAP devices, Audiorective Filter, Delay and EQ inserts, controller points, track volume automation, arrangement markers in seconds, Session scenes and slots, channel mute/pan/solo, master volume, fixed or step tempo, time signature, and WAV audio in 8, 16, 24 and 32-bit integer or 32 and 64-bit float. The MIDI writer accepts note on/off, control change, pitch bend, program change, channel pressure and polyphonic key pressure; other messages fail on save.

Everything else in a file is kept, not rejected. When the file comes from another application, or holds content the model has no field for (a folder track, a Vst3 plug-in, tempo ramps, automation lanes, warped audio, a disabled clip, `color` and `comment`, other `MetaData` fields), `openDawProject` returns a warning that names each kind (`Kept in the file unchanged, not played or edited: ...`) and the next save writes **only what the project changed since it was opened** into the file's own XML: a moved clip changes that clip's `time` and nothing else, and the other tracks, scenes, plug-in presets, IDs and the other application's name come back as they were. A save with no edit leaves `project.xml` the same tree (the same elements, attributes and order), every other archive entry byte for byte, and adds one `audiorective/` sidecar entry; `metadata.xml` is written again with the same content. A change the file cannot take (tempo steps in a file whose tempo ramps, beat-based markers, a Session clip into a slot that holds a clip the model does not carry) is refused on save with an error that names the cause. What is kept and not played is silent in Audiorective: a Vst3 effect, a pre-fader send or a stretched clip is not heard. The full element-by-element table, with what each row was verified by, is [DAWproject support](/docs/dawproject-support/). Bitwig Studio 6.1.7 opens the files this package writes, and this package reads a file edited in Bitwig and exported back (moved clip, changed note, mute, volume, and every tempo, meter, marker, scene, loop, window, gain, fade and trim value equal); Bitwig does not keep this package's `audiorective/` sidecar folder, so extension data and device state stored there do not survive a trip through Bitwig. Cubase and Studio One files were read, not opened in the application.

**Audio clips in Bitwig's form.** Bitwig writes every audio clip as an outer `Clip` (place, length, name, fades; `playStart` in beats) around a `Clips` with one inner `Clip` that holds the `Audio` directly, in a `Lanes` with a gain `Points`, or in a `Warps`. The reader takes such a clip as an ordinary audio clip when the audio runs at its original speed: the inner clip's `playStart` and `playStop` are the part of the file in seconds, the outer clip's `time` and `duration` (beats are converted through the tempo map, so a clip across a tempo change keeps its seconds) and its fades are the clip's, and a flat gain curve is the clip gain. With `Warps` the points must be the identity: at the clip's start and end and at every tempo change inside it, audio seconds advance exactly as timeline seconds do, within 1.5 frames of the recording (the slack covers Bitwig's float32 beat values: a 4 s clip at 100 BPM is written as 6.6666669845581055 beats; a real stretch of a few thousandths of a percent is outside it). A loop as long as the clip is no loop. A stretched clip (`Warps` that play the audio faster or slower than the tempo map) is read as a clip with `stretch` (see [Stretched audio from another DAW](#stretched-audio-from-another-daw)): ratio, anchors, the window of the original file, a varispeed placeholder until the Workspace's `stretch` engine renders it, and `Warps` rewritten from the time map on an edit (an unchanged clip keeps its XML). An audio window that is not as long as the clip and has no warp markers is not read, and neither are warp markers that run backwards or do not cover the clip. A moving gain curve of an unstretched clip whose audio starts at the file's start is read into the clip's `gainAutomation` and played; one inside a trimmed or stretched nested clip, a loop that repeats, several nested clips or a nested clip that does not cover the outer one is kept the same way, with its reason. An edit to a clip read this way is written into the same nested form (position and length on the outer and inner clip, the file window, fades, gain, name), and only the values that changed are written; a clip removed, duplicated or split follows the nested form of the file's other clips; a clip whose edit the form cannot say (a loop, a moving gain, other audio) is written in Audiorective's own form instead.

**Studio One.** A PreSonus Studio One 7.0.2 file opens: `<Project version="0.1">` (the label the DAWproject reference library used before 1.0) is read as 1.0 with a warning, the HTML entities of a short fixed table in `metadata.xml` (`&copy;` and the like) are read as their characters (any other entity is an error that names `metadata.xml`), a `Note` without `channel` plays on channel 0 with a warning, and what the model cannot hold stays in the file with a reason: a clip with a note before the start of its content (a negative `time`), volume automation with two points at one time (a step), a clip without `duration`. `pnpm --filter @audiorective/daw probe:studio-one` downloads the public file, checks its hash and prints what it reads.

Every `project.xml` and `metadata.xml` this package writes is validated against the official `Project.xsd` and `MetaData.xsd` in the test suite (the `xmllint-wasm` dev dependency). A public Cubase 14 export ([Steinberg forum](https://forums.steinberg.net/t/import-and-export-of-media-projects-and-dawprojects/1010846), inner `test.dawproject` SHA-256 `b45bdefe6101b58db1aad86757801d816350c9b6c0eb7b9ff5a9f55edea25708`) opens, takes a new clip and writes back its folder track, standalone master channel, EQ devices and presets: after building the daw package, `pnpm --filter @audiorective/daw probe:cubase` downloads the file, verifies its hash and repeats the check; pass a previously downloaded inner `.dawproject` to run offline. The same holds for `probe:studio-one` (a Studio One 7.0.2 export, SHA-256 `d8828597df45c590faa1c73dbfc02cf2aaffc43b924044e73c6a42e0e58675de`; pass the downloaded file to run offline).
