What `@audiorective/daw` does with each part of a [DAWproject](https://github.com/bitwig/dawproject) file, measured against the official `Project.xsd` and `MetaData.xsd`. The rule behind every row: the model carries what it can play and edit; everything else in a file from another application is kept in that file's own XML and archive, listed in the open warnings, and written back on save. Nothing is dropped silently.

What was checked in real Bitwig Studio 6.1.7. In demo mode: opening the files this package writes. That test found three problems, now fixed in the writer: fades are written in beats (Bitwig read seconds as beats), the arrangement timeline is written in beats so clips and markers stay in place under tempo changes, and clip gain is also written as a standard gain curve. With a licence (2026-11-26): a song this package wrote, edited in Bitwig (a clip moved, a note changed, mute and volume set) and exported back, reads correctly here; tempo, meter, markers, scenes, loops, windows, gain, fades and trims all equal what was written, and Bitwig's own audio clips (a project made in Bitwig with a click recording, and the clips of the exported song) are read as audio clips; Bitwig-written MIDI and stems import correctly (see the MIDI export row below). Bitwig drops this package's `audiorective/` sidecar folder: extension data, WebCLAP bundle locations and the private details stored there do not survive a trip through Bitwig. Cubase has no Linux version and needs activation, so nothing was opened there. A PreSonus Studio One 7.0.2 export was read (not opened in the application): see Studio One below.

## How a file from another application is handled

`openDawProject` and `openDawProjectBlob` read a file whose `Application` is not Audiorective, or that holds anything the model has no field for, in _keep mode_:

- The file's own `project.xml` and `metadata.xml` stay in memory. The model reads the parts it carries; the rest (unknown plug-ins, `color`, `comment`, folders, tempo ramps, automation lanes, a second master, ...) is not in the model and is listed in one warning: `Kept in the file unchanged, not played or edited: ...`.
- On save, the codec compares the project with what it was when opened (or last saved) and writes **only the difference into the file's own XML**. A moved clip changes that clip's `time`; a new track is inserted after the last other track (the model lists the master apart); a removed track takes its lane and slots with it; every other element, attribute, ID, whitespace-free ordering and archive entry stays as the other application wrote it. A new element gets IDs and file paths that do not clash with the file's.
- An edited clip keeps its own attributes the model does not write (`color`, `comment`, `enable`) and the attributes of every note it still has (`rel`); its content (`Notes`, `Points`) is rewritten from the model, except the `Points` the model could not read, which stay.
- A change the file cannot take is refused when saving, not dropped: tempo steps in a file whose tempo automation has a real ramp or is in seconds, a Session clip into a slot that holds a clip the model does not carry, a master volume in a file with no master channel. The error names the cause.
- A song-wide time edit (`rippleDelete`, an inserting `copyRange`) moves the content the file keeps as it moves the content the model carries, in the unit the element is written in: a kept clip (a clip the model cannot play, or one on a track it does not carry) by the beats of the range in a beats lane and by its seconds in a seconds lane, a kept `Points` lane (an automation of a parameter the model does not model, a tempo or time signature lane it cannot read) point by point. A save writes the moved `time`; undo puts the file's own text back. What cannot be moved correctly is never saved out of step: the edit is refused before anything changes (`Project ripple delete is blocked by kept content: …`, `Project copyRange is blocked by kept content: …`) when a kept clip lies across the removed range, inside the copied range or across the insert point (it cannot be trimmed, copied or split), a kept lane has a point inside the removed or copied range, or kept content is written in a unit other than seconds or beats. A kept clip with no `duration` counts as the part of its content `playStop` names, or as a point. A clip an `applyEdits` request moves, resizes or creates must not land on a kept clip either (`code: "overlap"`).
- A file written by Audiorective itself with nothing extra is written from the model, as before.

A clip the model cannot play or edit (audio whose nested form the model cannot say, a disabled clip, audio the browser cannot decode, a clip that holds only `Points`, a MIDI clip with a note before its content start) is left out of the model: it is silent in Audiorective, untouched in the file, and the warning says which case it is.

A save with no edit leaves `project.xml` the same tree (the same elements, attributes and order) and every other archive entry byte for byte (folder entries are not written), and adds only entries under `audiorective/`. `metadata.xml` is written again with the same content: it is re-serialised, so an HTML entity such as `&copy;` comes back as the character it names.

## Support matrix

Columns: **Read** the model takes it from the file; **Edit** a public API changes it; **Round trip** it comes back from open, edit elsewhere and save; **Play** the Workspace plays it; **Render** `renderMixRange`, `renderSession` and the audio fallback include it. ✅ yes, ◐ partly (see the note), ❌ no, n/a does not apply. "Kept" means the content stays in the file and is not in the model. **Bitwig 6.1.7** and **Cubase** say whether the host opened a file this package wrote and showed the row correctly (for Bitwig also whether this package read the row back from Bitwig's own export or file): ✅ shown as expected, ◐ shown with the noted difference, ❌ not honoured, "not checked" means the test files did not exercise it.
